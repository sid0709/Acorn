## 1. What Acorn is

Acorn is a Chrome MV3 extension with a native side panel that applies to jobs on any website. The main action is **Run**: one click, and the agent (§19)

1. looks at the page in the active tab as a screenshot,
2. opens the application (clicks Apply),
3. fills each page from the user's Acorn profile with real mouse and keyboard events (text, dropdowns, radios, checkboxes),
4. attaches a résumé from the user's Library,
5. clicks Next / Submit, and
6. stops on the confirmation page, or says why it could not finish and what the person must do (a CAPTCHA, an emailed code, a document it does not have), then carries on, in the same conversation and with its notes, when they press Continue (§19.6a).

Four design rules run through the whole codebase:

- **No per-site rules.** Nothing matches vendor class names, hostnames, ids, or button wording. Code reads page _structure_ (ARIA roles, native inputs, dialogs, layout); every _judgment_ ("what page is this?", "which control moves forward?", "which option is the answer?") is a model decision. (See also the memory note "No hardcoding in the agent".)
- **Two models with separate jobs.** A text model writes (free-text answers). A decision model, TypeSafe **Jev**, only chooses among things that already exist and returns probabilities. The backend wraps Jev as the **SelectorGateway**.
- **Bring your own key.** Every model call uses the OpenRouter API key saved on the user's Acorn profile. The server has no AI key of its own.
- **The Chrome tab id is the session key.** All state is per tab, and several tabs can run at once.

The other apps around it:

- **acorn-frontend** (Next.js, `localhost:6005` / `acornapply.com` and `www.acornapply.com`): where the user signs up, edits the profile (including the OpenRouter key, the **extension password**, and the **default account password** for job sites), uploads Library résumés and cover letters, and connects Gmail. It also serves `GET /api/extension/latest`, which the sidebar uses for its update notice.
- **acorn-admin** (`:6010`): the support console. It reads support claims (with the captured session), and can open a support session as a user.

## 4. Extension runtime

### 4.1 Manifest and build

[`manifest.json`](../../extension/manifest.json) declares:

| Permission             | Why                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| `sidePanel`            | The UI is a native side panel; the toolbar icon opens it (`setPanelBehavior({ openPanelOnActionClick })`).    |
| `storage`              | `chrome.storage.local` (session, settings) and `chrome.storage.session` (per-tab state).                      |
| `unlimitedStorage`     | The per-tab log lives in IndexedDB with no cap.                                                               |
| `scripting`            | Re-inject the content script into open tabs and new navigations; full-page screenshot helpers.                |
| `webNavigation`        | List a tab's frames, watch navigations (frame reloads, SPA history changes).                                  |
| `alarms`               | Keep the MV3 service worker alive while the panel is open or work is in flight.                               |
| `debugger`             | Drive the agent Run: screenshots, real mouse and keyboard input, file pickers, and the browser's own dialogs. |
| `activeTab`            | Capture the visible tab for support screenshots.                                                              |
| `<all_urls>` host perm | The content script runs on every site; the API and site hosts are listed explicitly too.                      |

The content script is declared for `<all_urls>` with `all_frames`, `match_about_blank`, and `match_origin_as_fallback`, at `document_idle`. Because a declared content script does not reach tabs opened before install and some SPA navigations, the worker also injects it programmatically ([`inject-content.ts`](../../extension/src/inject-content.ts)) on `webNavigation.onCommitted`, `onHistoryStateUpdated`, `onInstalled`, and at worker start into every open tab (skipping `chrome://`, the Web Store, etc.). A boot flag on `window` (`__acornContentBoot`) keeps a frame from initialising twice. **Boot is made to survive its own failures:** the startup steps (selection chip, support handoff) are independent, each caught and traced (`boot:error`), so one failing step (a page's content policy refusing what the chip draws) cannot keep the other from starting. The window flag is a liveness check (`() => Boolean(chrome.runtime?.id)`), not a bare `true`: after an extension reload an earlier script stays in the page but cut off from the extension, and a flag that only said "started" would stop the new script from starting there. Every injection returns its result (frames reached, or the error) and a failure is written to the tab's log (`inject:error`); it is never swallowed.

Build ([`vite.config.ts`](../../extension/vite.config.ts)): Vite + `@crxjs/vite-plugin`. The version is read from `package.json`, written into the built manifest, exposed as `import.meta.env.VITE_ACORN_VERSION`, and printed on every build. `VITE_*` settings come from `acorn/.env`:

| Variable                        | Effect                                                                                                                                                                      |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_ACORN_API_URL`            | API origin. Default from `@acorn/shared/api`: `http://127.0.0.1:8083` in development, `https://api.acornapply.com` otherwise.                                               |
| `VITE_ACORN_WEB_URL`            | Site origin. Default `http://localhost:6005` / `https://acornapply.com`. Used for the update check and support handoff.                                                     |
| `VITE_ACORN_AGENT_URL`          | Where acorn-agent runs (§19). Default `http://127.0.0.1:8090` in a development build, `https://api.acornapply.com` otherwise (nginx sends `/agent/v1/` there to the agent). |
| `VITE_ACORN_DEBUG`              | Development builds only: always use the build's API URL (ignore the Settings value) and (no longer reports capture uploads: there are none).                                |
| `VITE_ACORN_AUTO_FOCUS_SECONDS` | Seconds each run tab stays in front under Auto-Focus. The code default is **4** (`AUTO_FOCUS_DEFAULT_SECONDS`); `.env.example` says 2.                                      |

`bun run dev:acorn` watch-builds to `acorn/extension/dist` in development mode (old hashed files are kept so a run in progress keeps its content script); `bun run build:acorn` is the production build. File names carry no hash in either build (`assets/[name].js`): an extension that is already running keeps asking for the names of the build it was loaded from, and a rebuild that renamed them left every page opened afterwards with no content script until the extension was reloaded.

### 4.2 Service worker

[`background.ts`](../../extension/src/background.ts) does this at start:

- Creates the `acorn-socket-keep-alive` alarm (every 30 s). On each tick it pings `chrome.runtime.getPlatformInfo()` while a side panel port is open, and redials the socket if it is down. A second alarm, `acorn-work-keep-alive`, runs only while any tab has a run or a generate in flight ([`work-state.ts`](../../extension/src/background/work-state.ts)).
- Accepts the side panel's long-lived port (`acorn-sidebar`), pushes socket status over it, and dials the socket.
- Connects the socket, redials immediately when the browser comes back `online`.
- Enables "open side panel on toolbar click", binds content-script injection and the Auto-Focus setting, and injects into open tabs.
- Drops per-tab logs of tabs that no longer exist.
- Tab lifecycle: `tabs.onRemoved` unbinds the tab's job, pipeline progress, and log. `tabs.onReplaced` (prerender swaps) re-keys every per-tab map and in-memory set from the old id to the new one.
- `storage.onChanged` on `acornApiUrl` or `acornSession` reconnects the socket (debounced 200 ms).
- `runtime.onMessage` → [`message-router.ts`](../../extension/src/background/message-router.ts).

Messages the router handles (constants in [`types.ts`](../../extension/src/types.ts) `MSG`):

| Message                                              | Sender → handler                              | What it does                                                                                                                                                                                    |
| ---------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acorn:start-run`, `acorn:stop-run`                  | sidebar → `messages/run.ts`                   | Start the agent Run on a tab (a test may pass `stopBeforeSubmit`); abort it.                                                                                                                    |
| `acorn:answer-run`                                   | sidebar → `messages/run.ts`                   | The person's answer to the question a Run is waiting on.                                                                                                                                        |
| `acorn:support-handoff-relay`                        | content (Acorn site only) → `support-session` | Redeem a support sign-in code.                                                                                                                                                                  |
| `acorn:submit-support-claim`                         | sidebar → `messages/support-claim.ts`         | Full-page screenshot + notes → new claim or follow-up message.                                                                                                                                  |
| `acorn:refresh-tab-usage`                            | sidebar → `tab-usage-store.ts`                | Reconcile a tab's AI usage with `GET /acorn/ai-usage`. Nothing in the sidebar calls it since 1.94.0 (the AI usage list left the Jobs tab); the handler stays for the next place usage is shown. |
| `acorn:auth-status`, `acorn:auth-signin`, `-signout` | sidebar → `messages/auth.ts`                  | Session state, sign in with email + extension password, sign out.                                                                                                                               |
| `acorn:socket-status`, `acorn:reconnect-socket`      | sidebar → `messages/auth.ts`                  | Socket state; force a dial.                                                                                                                                                                     |
| `acorn:debug-trace`                                  | content → `debug-trace-sink.ts`               | A page trace event: written to the tab's local log (it is not uploaded).                                                                                                                        |

Handlers that start work reply `{ ok: true }` immediately and report progress asynchronously through `broadcastPipelineProgress(tabId, progress)` ([`socket-connection.ts`](../../extension/src/background/socket-connection.ts)), which:

1. emits `pipeline:progress` on the socket (the server relays it to the account's other clients),
2. merges it into `acornTabPipelines` in `chrome.storage.session` (serialized per tab), and
3. sends `acorn:pipeline-progress` to the side panel.

### 4.3 Content script

[`content/index.ts`](../../extension/src/content/index.ts) runs in every frame. On the Acorn site only, it starts the support handoff listener ([`support-handoff.ts`](../../extension/src/content/support-handoff.ts)), and writes the extension's own page errors to the tab's log (`page:error`). It answers no message from the worker: the agent Run does not use it, since it sees the page as a screenshot and acts through the debugger (§19). Until v1.83.0 the content script also serialized the DOM, ran plan steps, and clicked controls for the page-reading Run; that code was removed.

### 4.4 Side panel

The panel is a React app ([`sidebar/main.tsx`](../../extension/src/sidebar/main.tsx) → [`SidebarApp.tsx`](../../extension/src/sidebar/SidebarApp.tsx)) built from `sid-ui`. Signed out, it shows the sign-in card ([`SignInCard.tsx`](../../extension/src/sidebar/SignInCard.tsx)). Signed in:

- **Header**: the live Acorn Face, a busy-workers count, and an account menu (Acorn Face guide, Settings, Report, Sign out / End support session). The avatar dot is the socket state. The Report dialog closes and discards its notes when the active browser tab changes, and starts empty each time it opens.
- **Nav** (`PillNav`, hash routed): **Jobs**, **Support**, **Logs**.
- **Jobs**: the **Auto-Focus** switch, the **Now card** for the active tab, and the **Page map** of the page the run is on ([`RunMapCard.tsx`](../../extension/src/sidebar/RunMapCard.tsx)). The map is always there: an empty page before the first run, the live page while a run works, and the last page once it ended, so a run can be followed and read back; 19.4m says what it draws. The Activity feed and the AI usage list that sat here until 1.93.0 are gone (the Logs tab has the raw log). On the Jobs tab the Now card shows **Run** (or "Run again"), **Continue** after a stopped run, and **Stop** while running. While a run works, the card shows its timer, step and cost, and the stop reason when it fails.
- **Support**: the user's claims, threads, and unread replies (pushed over the socket).
- **Logs**: the per-tab log (IndexedDB `acorn-tab-log`), grouped by run: DOM tree stats, compressed and meta trees, analysis, **every backend call** (request, answer, status and latency, or why it got no answer), the run's **decisions** and what they rested on (`decision` entries: why it clicked, waited, or stopped), plan, every trace event, and errors that were caught. Each entry carries its level, run, step, page, duration, and a group that links a call's request, answer and decision. Filter by view (All / Problems / Run / AI / Trees), search titles and contents, copy, or **Download** the whole log (not only what the view or search shows) as one compressed zip (each entry deflated; typically a tenth of the size) that opens with `00-summary.json` (each run's outcome, reason, durations per phase) and `01-index.json`. It stays in the browser; see §12.7.
- **Settings drawer**: socket state, Acorn version, and the API URL (saved to `chrome.storage.local`; ignored by debug builds).
- **Update dialog**: on open, the panel asks `GET <site>/api/extension/latest` once; when its version is newer than `VITE_ACORN_VERSION`, a dialog links to the download.
- **Notices**: expected failures and results are toasts (`pushAcornNotice` / `broadcastOperatorNotice`). A notice with a `tabId` shows only while that tab is focused.

The panel never holds work state of its own. It reads `chrome.storage.session` on open, follows `storage.onChanged` and `acorn:pipeline-progress`, and sends start/stop messages. Closing the panel does not stop a run.

## 5. Sign-in, sessions, and the socket

### 5.1 Extension sign-in

```text
Side panel                    Service worker                       acorn-backend
──────────                    ──────────────                       ─────────────
email + extension password ─▶ acorn:auth-signin ─▶ POST /acorn/auth/extension/signin {email, password}
                                                     • find account by email (or by profile email)
                                                     • profile.extensionPassword must be set and equal
                                                       (constant-time compare)
                                                     • StartSession → random token, stored as SHA-256 hash,
                                                       30-day TTL (acorn_sessions)
                              ◀── { token, session{username, displayName, profileId} }
                              chrome.storage.local.acornSession = {accessToken, …, expiresAt: ""}
                              chrome.storage.local.acornApiUrl  = the base used
                              connect socket
◀── signed in (toast)
```

- The **extension password** is a separate secret the user sets on the Acorn profile (site → Account tab). It is not the website password. The signed-in email may be the account email or the profile email.
- Signing out calls `POST /acorn/auth/signout` (revokes the session) and clears local storage; the website session is untouched.
- The API URL is the Settings value, else the build default; retired hosts are ignored ([`acorn-auth.ts`](../../extension/src/auth/acorn-auth.ts)).
- Server side, `account.Store.Session` looks up the token's SHA-256 hash, caches a checked session for 30 s, and rejects expired or deactivated accounts. The extension keeps `expiresAt: ""` for normal sessions, so it learns about expiry from a 401 or a socket auth error ("Session expired").

### 5.2 Support sessions

An admin in acorn-admin can start a **support session** for a user. The flow uses `window.postMessage` on the Acorn site only ([`content/support-handoff.ts`](../../extension/src/content/support-handoff.ts), [`@acorn/shared/api`](../../packages/shared/api.ts)):

1. The site page posts `acorn:extension-ping`; the content script answers `acorn:extension-hello` with the account it is signed in as.
2. If that is not the support session, the page posts `acorn:support-handoff` with a one-time code.
3. The content script relays it to the worker, which accepts it only from the top frame of a known Acorn site origin, redeems it at `POST /acorn/auth/support/redeem`, stores the user's own session as `acornSessionBeforeSupport`, and switches to the support session (which has an `expiresAt`).
4. Signing out of a support session (or its expiry) restores the user's own session.

A support session cannot delete the account; every model call it makes is recorded with `supportBy`.

### 5.3 Every API call

`authHeaders(tabId)` adds:

- `Authorization: Bearer <token>`,
- `X-Acorn-Client: extension/<version>` (usage stats tell the extension from the site),
- `X-Acorn-Tab: <uuid>` when the call is about a tab. The UUID is created per Chrome tab and kept in `chrome.storage.session` (`acornTabUsageKeys`); it survives panel reloads but not a browser restart. The backend uses it to file AI usage and process capture per tab.

### 5.4 The Socket.IO connection

[`acorn-socket.ts`](../../extension/src/acorn-socket.ts) owns one socket per worker:

- Origin = the API host; path `/acorn/socket.io`; `auth: { token }` in the handshake (query-string tokens are never accepted because URLs reach proxy logs); query `type=extension`.
- Transports websocket first, then long-poll; socket.io reconnection with 1 s → 30 s backoff and ±50 % jitter; 20 s connect timeout. When the server refuses the token or kicks the socket (cases socket.io does not retry), the extension schedules its own redial with the same backoff, reading a fresh token.
- A connection notice appears only for outages longer than 5 s ("Reconnecting…", then "Reconnected"), or "Session expired" for auth errors.

The server side ([`gateway/gateway.go`](../../../acorn-backend/acornapi/gateway/gateway.go)) authenticates the handshake token as an Acorn session and puts the socket in the room `acorn:acct:<accountId>`. Everything stays inside that room, so one account can never see or drive another's browser.

| Event                              | Direction                 | Purpose                                                                                           |
| ---------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------- |
| `ai-usage:recorded`                | server → extension        | `{ tab, entry }` for every model call recorded; the worker appends it to that tab's usage ledger. |
| `support:message`, `support:claim` | server → extension        | A claim changed; the worker forwards `acorn:support-claims-changed` to the panel.                 |
| `pipeline:progress`                | extension → server → room | Relayed to the account's other clients.                                                           |
| `clients:update`, `connected`      | server → room             | Who is connected.                                                                                 |

The `dom:*` events of the original "UI board" that drove the extension remotely (`dom:tree`, `dom:highlight`, `dom:get-content`, `dom:execute-actions`, `dom:plan-step`) were removed with the page-reading Run: the server no longer relays them. The Run goes on inside the extension and the agent server and reports to the backend over HTTP.

### 5.5 Keeping MV3 alive

A service worker may be stopped when idle. Acorn keeps it running with: the side panel's port (`acorn-sidebar`, re-attached if it drops), the 30 s keep-alive alarm while the panel is open, and the work alarm while any tab works. The socket state shown in the panel comes from the port plus a 3 s poll.

## 6. Per-tab state

Everything that belongs to a tab is keyed by its tab id. Writes to a shared map go through a per-key promise lock ([`storage-lock.ts`](../../extension/src/storage-lock.ts)).

| Store                                                                           | Key                                                        | Holds                                                                                                                                                        |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `chrome.storage.local`                                                          | `acornSession`, `acornSessionBeforeSupport`, `acornApiUrl` | Sign-in and API URL.                                                                                                                                         |
| `chrome.storage.local`                                                          | `acornAutoFocus`                                           | Run switches (per browser).                                                                                                                                  |
| `chrome.storage.session`                                                        | `acornTabPipelines`                                        | Each tab's latest `PipelineProgress` (phase, message, run state). The panel renders this.                                                                    |
| `chrome.storage.session`                                                        | `acornKeptAgentRuns`                                       | A stopped agent Run that Continue can take back up (session id, log id, tab, `stopBeforeSubmit` flag, and the run's memory), under each tab it used.         |
| `chrome.storage.session`                                                        | `acornTabUsageKeys`, `acornTabUsage:<key>`                 | Per-tab usage key and the usage ledger view.                                                                                                                 |
| IndexedDB `acorn-tab-log`                                                       | entries indexed by tab                                     | The Logs tab. Cleared when the tab closes; moved to the tab a run goes on in. Keeps each tab's last 5 runs and at most 50 MB of text, oldest runs first out. |
| Worker memory ([`work-state.ts`](../../extension/src/background/work-state.ts)) | `pipelineRunningTabIds`, `runTabIds`, run stop controllers | What is in flight right now.                                                                                                                                 |

Rules ([`policy-acorn.md`](../../policy-acorn.md) §1):

- One tab runs one Run at a time (a second start is refused). Different tabs run in parallel.
- When a Run starts, its tab is put in a Chrome tab group with a random color, titled `Acorn <first 6 hex characters of the tab's usage key>` ([`run-group.ts`](../../extension/src/background/run-group.ts), `tabGroups` permission). A tab opened from a tab in such a group (`webNavigation.onCreatedNavigationTarget`, which a tab the person opens with Cmd+T or + never raises) joins that group, whether or not the run follows it; a new tab with no such event is taken out of any Run group within 3 s. Tabs that cannot be grouped (pinned) are left alone.
- A Run can move to a tab it opened (an Apply that opens a new tab). The run "claims" that tab: progress is emitted to every claimed tab, Stop works from any of them, and the job binding is re-keyed to it.
- The agent follows a tab the page opens (§19.2), and `tabs.onReplaced` (Chrome swapping a tab) re-keys the run, the tab's job binding, usage key, progress and log to the new id; the log of a tab the run left moves with it ([`moveTabLog`](../../extension/src/tab-log-session.ts)).
- The extension never opens tabs of its own.

## 7. Reading a page

The extension does not read a page as text. The agent Run sees it as a **screenshot** ([`agent/capture.ts`](../../extension/src/agent/capture.ts)) plus a short report about the control that has focus ([`agent/page-info.ts`](../../extension/src/agent/page-info.ts)), and the model decides from the picture (§19.2, §19.4). Until v1.83.0 the content script also serialized the page's DOM into a node-numbered tree, listed its fields and their issues, chose the form frame, and sent planner trees to the models; all of that, and everything built on it, was removed.

## 11. Résumés, cover letters, and file formats

### 11.1 The résumé gate (removed)

The page-reading Run chose a résumé before it touched a page. The agent chooses its own from the Library list it receives with its session (§19.4c).

### 11.2 Recommend

[`resume.Recommend`](../../../acorn-backend/resume/recommend.go) + [`selector.MatchPosting`](../../../acorn-backend/selector/gateway.go): the Library's résumés are grouped into **stacks** (same title, several formats); each stack is described by its title and up to 20 analyzed skills. The title is the file's **alias**, set at upload in the web app's Library ([`resume-library.tsx`](../../../acorn-frontend/components/workspace/resume/resume-library.tsx)): a single file (one at a time) asks for it in a modal, starting from the file name; a folder upload uses the file's path below the picked folder plus its name, lowercased and joined by dashes ([`library-alias.ts`](../../../acorn-frontend/components/workspace/resume/library-alias.ts)), so `Resume/FullStack/Java/David.docx` picked as `Resume` becomes `fullstack-java-david.docx`. The alias is the `stack` the extension lists for each recommendation. One Jev call asks two questions: is this text a job posting (P ≥ 0.5, else HTTP 422 "No job description on this page"), and which résumé fits (by tech stack, domain, required skills). There is no threshold: the most probable stack is recommended, and the top 3 with probabilities are shown on the Now card.

### 11.3 Which file is attached

The agent attaches the Library file the model names, fetched from `GET /acorn/agent/resumes/:id` (§19.12). Library files carry their other formats as `variants`.

### 11.4 Cover letters

The server-side cover-letter pick (`POST /acorn/custom/cover-letter`) was removed. The agent sees the Library's cover letters as files typed `cover_letter` and chooses among them (§19.4c, §19.12).

### 11.5 File formats

The agent's [`upload.ts`](../../extension/src/agent/upload.ts) sets the file on the input the click opened (§19.2); the file list it is given names each file's format.

### 11.6 Generate (server only)

The backend still has résumé generation (`POST /acorn/custom/generate`, its `/continue`, and the polled `GET`). The extension no longer calls it: the code and the buttons that started it were removed.

## 12. The backend (acorn-backend)

### 12.1 Process

[`cmd/server/main.go`](../../../acorn-backend/cmd/server/main.go) loads `acorn-backend/.env`, connects to MongoDB (database `ACORN_DB`, default `AcornDB`), builds the stores, ensures their indexes in parallel, starts process capture (MongoDB, plus a local folder when `ACORN_DEBUG_DIR` is set), mounts `acornapi` at `/acorn` (and Google sign-in at `/v1/auth/google`), warms the TLS connection to OpenRouter's Decisions API, and serves on `HTTP_ADDR` (default `127.0.0.1:8083`). CORS allows the site and console origins; the extension is not a browser origin and uses bearer tokens. Request bodies are capped at 16 MB. All model routes are behind the `acorn_ai` kill switch (`KILLSWITCH_ACORN_AI=off` answers 503).

### 12.2 Routes the extension calls

| Route                                                                                                  | Purpose                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /acorn/auth/extension/signin`                                                                    | Email + extension password → session token.                                                                                                                                                                                                        |
| `POST /acorn/auth/signout`, `GET /acorn/auth/me`                                                       | Revoke / describe the session.                                                                                                                                                                                                                     |
| `POST /acorn/auth/support/redeem`                                                                      | Redeem a support handoff code.                                                                                                                                                                                                                     |
| `POST /acorn/qa`                                                                                       | Writer answer to one question (the extension no longer calls it).                                                                                                                                                                                  |
| `POST /acorn/custom/recommend`                                                                         | Recommend a Library résumé for a job posting.                                                                                                                                                                                                      |
| `POST /acorn/custom/generate` (+ `/continue`, `GET` poll)                                              | Résumé generation.                                                                                                                                                                                                                                 |
| `GET /acorn/custom/library-resumes/:id` (+ `/preview`), `/custom/resumes/:generationId` (+ `/preview`) | Library or generated file `{file:{key,name,mimeType,base64,label,format,variants}}`, with an `ETag` and `304 Not Modified` for `If-None-Match` (as is `GET /acorn/jobs/:jobId/recommended-resume`); HTML previews.                                 |
| `GET /acorn/jobs/:jobId`, `/jobs/:jobId/recommended-resume`, `/jobs/:jobId/resume-preview`             | Worker Pool job (with stored JD) and its résumé.                                                                                                                                                                                                   |

| `GET /acorn/profile`                                                                                   | The profile (the sidebar reads `defaultAccountPassword` to show it on account steps).                                                                                                                                                              |
| `GET /acorn/ai-usage?tab=…`, `GET /acorn/ai-usage/:id`                                                 | A tab's usage list (exact `costNanos`/`totalNanos`) and one entry.                                                                                                                                                                                 |

The site and console use the rest: profile editing and import from a résumé (`/acorn/profile`, `/profile/from-resume`), the résumé config/templates/generations/Library (`/acorn/resume/*`), Gmail connect and labels (`/acorn/gmail/*`), Google sign-in, and `/acorn/admin/*`.

### 12.3 Where the AI comes from

For each request, [`acornapi/model.go`](../../../acorn-backend/acornapi/model.go) loads the account's profile and builds:

- the **text model**: `openai.OpenRouter(key)` — OpenRouter's OpenAI-compatible chat API, model `openai/gpt-6-luna` (`acorn-backend/config.OpenRouterModel`), reasoning off, JSON-schema outputs;
- the **decision model**: `jev.New(key)` — `typesafe/jev-1.13` at `https://openrouter.ai/api/alpha/decisions` (`config.JevModel`, `config.OpenRouterDecisionsURL`), wrapped as `selector.Gateway`.

An account without a key gets "Add your OpenRouter API key in profile settings" (503 on the Q&A, generate, and recommend routes; the extension no longer calls the Q&A route).

**Error codes.** Every failed model call carries a stable `code` beside its message ([`acornapi/errcode.go`](../../../acorn-backend/acornapi/errcode.go), `modelErrorCode`): `openrouter_no_key` (503), `openrouter_invalid_key` (OpenRouter 401/403), `openrouter_no_credits` (OpenRouter 402, answered **402**), `openrouter_rate_limited` (429), `provider_error` (5xx or unreachable), `model_timeout`, `model_bad_answer` (unparseable or empty), `model_unavailable` (no model configured), plus `signed_out` (401) and `kill_switch` (503). The provider's refusal keeps its status (`openai.StatusError`), so a spent balance is told apart from a bad key. Routes that answer 200 with `ok:false` (the run's decision routes) carry the same `code`. The extension turns codes into words ([`user-messages.ts`](../../packages/shared/user-messages.ts)); the messages beside them are for logs and may change.

### 12.4 Usage metering

`withUsage` attaches a recorder to the request context: every model call (text or Jev) is written to `acorn_ai_usage` with account, tab key (`X-Acorn-Tab`), route, feature (`ask`, `recommend`, `resume_generate`, `resume_analyze`, `profile_import`, `gmail_label`; rows from before v1.83.0 also carry `fill`, `run`, and `custom_job`), client and version, support admin, tokens (prompt, completion, cached), cost in nanodollars, duration, status. Right after it is stored, the entry is pushed to the account's sockets as `ai-usage:recorded { tab, entry }`. The worker's [`tab-usage-store.ts`](../../extension/src/background/tab-usage-store.ts) appends it to that tab's ledger (max 100 entries) and its `chrome.storage.session` view, so the panel's usage list updates live; `GET /acorn/ai-usage` reconciles.

### 12.5 The socket gateway

See §5.4. The Go server uses `zishang520/socket.io` v3 with a 16 MB message buffer; the handshake token is checked against the session store with a 10 s timeout.

### 12.6 Persistence

All data is in MongoDB (`AcornDB`):

| Collection                                                                 | Contents                                                                                                   |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `acorn_accounts`, `acorn_sessions`, `acorn_google_states`                  | Accounts (argon2id password hashes), sessions (SHA-256 token hashes, 30-day expiry).                       |
| `acorn_profiles`                                                           | The profile document, including the OpenRouter key, default account password, extension password.          |
| `acorn_resume_library`, `_configs`, `_templates`, `_generations`, `_tasks` | Library files (résumés and cover letters), résumé pipeline config, templates, generated files, task state. |
| `acorn_ai_usage`                                                           | One row per model call (no prompt bodies).                                                                 |
| `acorn_debug_traces`                                                       | Process capture, gzipped, per user + tab, expiring after 72 h.                                             |
| `acorn_support_claims`, `_messages`, `_attachments`, `_debug_logs`         | Support reports, screenshots, and the extension's gzipped log sent with each report.                       |
| `acorn_gmail_mailboxes`, `_oauth_states`, `_label_guides`                  | Connected Gmail mailboxes (refresh tokens) and labeling guides.                                            |
| `acorn_admin_*`, `acorn_support_handoffs`                                  | Support console users, sessions, audit trail, handoff codes.                                               |

Library files are slow to read from Mongo (seconds per file; a development machine measured about 345 ms per round trip to a distant Mongo), so [`resume/file_cache.go`](../../../acorn-backend/resume/file_cache.go) keeps whole rows with their bytes in memory by account and id, up to 8 GB (`ACORN_LIBRARY_CACHE_MB`), the copies used longest ago dropped first. **The server is one process, so a copy is served until a write through it changes it** (a save, a delete, an account deletion; a file just saved is held at once). `ACORN_CACHE_TRUST_SECONDS` sets a window instead, for a deployment where another process can write: after it one query that skips the bytes (`uploadedAt`, `size`, names, `analyzedAt`, primary) says whether the copy is current, and only a changed file is read again. The account's list of rows (`reads`, without bytes) and the profile ([`profile/store.go`](../../../acorn-backend/profile/store.go), read when first asked for) follow the same rule. **Preload** ([`resume/preload.go`](../../../acorn-backend/resume/preload.go)): when the server starts it reads every account's Library files into memory in the background, the accounts with a valid sign-in first (`account.Store.RecentUserIDs`, newest first, up to 500), then the rest, most recently uploaded first, four accounts at a time, one query per account, stopping before the cap would be passed (the rest load on their first request). The server answers meanwhile. A read that began before a change to the account's Library is dropped, not kept. `ACORN_LIBRARY_PRELOAD=off` skips it. `GET /acorn/agent/resumes/:id` finds the stack from the cached rows and loads all its formats side by side, so a cold request is one read, not two in a row. Requests for one file at once share one read (singleflight), a stack's formats load side by side, a write through the process drops the copy, and a read is bounded to 60 s. The `ETag` of a Library or job résumé file is the hash of the versions it was built from, so a `304` costs no bytes read at all once the copy is warm. When Recommend picks a résumé it reads that stack and up to three cover-letter stacks into memory beside the request.

Worker Pool jobs come from the shared jobs catalog ([`acorn-backend/internal/jobs`](../../../acorn-backend/internal/jobs)).

### 12.7 Process capture and support reports

**The log stays on the device.** The extension no longer uploads its run timeline or page traces while it runs: the Logs tab (§6) is the whole record, and it holds what the server used to keep for debugging — the page text and controls sent to the decision model, the model's full answer (probabilities, usage), latency and status of every call, and the run's decisions. Backend responses carry what the extension cannot see (`ms`, server `timings`, the model's `kindProbabilities` and `verificationProbabilities`), never prompt text. The server-side recorder ([`debugtrace`](../../../acorn-backend/debugtrace/recorder.go), `POST /acorn/debug/*`) still exists for older extensions and for local development: with `ACORN_DEBUG_DIR=./debug-runs` it writes a folder per user and tab holding each model call (`ai-<purpose>.md`, `jev-<call>.md`) to disk, kept 72 hours in MongoDB when a database is configured.

**Report** (header menu) writes any queued log entries, takes a full-page screenshot (scroll-and-stitch, fixed elements shown once, JPEG ≤ 8 MB), and posts it with the notes, page URL/title, extension version, and tab key. **Submitting** is the only moment the log leaves the browser: the extension then gzips the tab's log (a summary plus every entry whole) and sends it to `POST /acorn/support/claims/:id/log` (`messageId` for a follow-up), which stores it unchanged with the claim (`acorn_support_debug_logs`, ≤ 12 MB gzipped), where admins download it. Opening the Report dialog uploads nothing. A follow-up on an open claim is a multipart message with the screenshot attached.

## 13. The models and what each one decides

### 13.1 Who decides what

| Decision                                                     | Model | Where                                                    |
| ------------------------------------------------------------ | ----- | -------------------------------------------------------- |
| Free-text answers, first person                              | text  | `acorn.Answer`, prompt `prompts/prose_system.txt`        |
| Is this text a job posting, and which Library résumé fits it | Jev   | `selector.MatchPosting`                                  |
| Gmail labels for a message (the site's labeling)             | Jev   | [`maillabel`](../../../acorn-backend/maillabel/label.go) |
| Everything the agent Run does on a page                      | text  | acorn-agent (§19), not acorn-backend                     |

Jev is asked typed questions (`choice` among keyed criteria, or `noul` = P(yes)) about a text `state`; it answers each with a choice, a confidence, and probabilities, and never generates text. Options are sent as keys (`option_0`, …) so labels round-trip exactly. A question lists at most 255 options. The client retries transient failures (3 attempts, 30 s timeout) on one shared keep-alive connection pool.

### 13.2 The writer

The writer prompt ([`prose_system.txt`](../../../acorn-backend/acorn/prompts/prose_system.txt)) returns short facts exactly as stored and writes prose answers in the first person, with rules against generic phrasing and a length matched to the question. `POST /acorn/qa` is one call (20 s) that sends the applicant profile first, then the question, so the provider can cache the prefix. Note that the prompt's hard rules allow the writer to **invent** employers, dates, metrics, or details when the profile is thin (see §14.4).

## 14. Data, storage, and privacy

### 14.1 What each party sees

| Data                                                 | Text model                                  | Jev                                        | Stored server-side                               |
| ---------------------------------------------------- | ------------------------------------------- | ------------------------------------------ | ------------------------------------------------ |
| Profile facts (name, contact, history, demographics) | yes (applicant JSON, for Q&A)               | no                                         | `acorn_profiles`                                 |
| Page text                                            | nothing (the extension no longer sends Q&A) | only the job posting text, for Recommend   | the tab's local log; a support claim if reported |
| Default account password                             | never                                       | never                                      | `acorn_profiles` (plain text)                    |
| Extension password, OpenRouter key                   | never                                       | never                                      | `acorn_profiles` (plain text)                    |
| Gmail contents                                       | never                                       | message rows, for the site's labeling only | Gmail refresh token in `acorn_gmail_mailboxes`   |

The agent Run (§19) sends the model a **screenshot** of the page and the applicant's `profile.json`; see §19.8 for who sees what.

### 14.2 How passwords stay out

- A password box's value is never read: the agent's report on the focused control replaces a password's value by its length (§19.2).
- No page HTML is ever sent. The agent's log entries carry kinds, places, and character counts, never typed text (§19.2).
- Calls are written to the tab's log with passwords, tokens, keys, and codes replaced.

### 14.3 Retention

- Extension: per-tab state in `chrome.storage.session` (cleared when the browser closes), per-tab logs in IndexedDB (cleared when the tab closes), session token in `chrome.storage.local`.
- Server: usage rows and profiles until deleted; sessions 30 days; a support claim keeps the log the person submitted with it.

### 14.4 Observations worth knowing

These are facts about the current code that are easy to miss:

1. **Run always sends the application.** There is no Stop before Submit setting in the sidebar. The runner and the agent still accept `stopBeforeSubmit` (the e2e test passes it), but the extension starts every Run with it off.
2. **Profile defaults on save.** [`profile.normalize`](../../../acorn-backend/profile/store.go) fills empty answers with defaults on every save: gender Male, orientation Heterosexual, citizenship U.S. Citizen, Hispanic/Latino No, race White, no sponsorship, no disability, not a protected veteran, over 18 Yes, background check Yes, relocate Yes, remote, no travel, notice "Immediately", public trust/clearance None. Applications answer EEO and eligibility questions with these when the user never set them.
3. **The writer may invent.** The prose prompt's hard rules let it make up employers, dates, metrics, and "friction" details when the profile is thin.
4. **Secrets in the profile are plain text** in `acorn_profiles`, and `GET /acorn/profile` returns them (OpenRouter key, default account password, extension password) to any valid session for that account, including support sessions.
5. **Capture is on by default in production** and stores the model calls (prompts and answers) per tab for 72 h (never page HTML).
6. **Usage detail has no bodies.** Usage rows store no request/response text, so the usage detail view shows its "recorded before request bodies were saved" placeholder.

## 16. Developing and debugging

```bash
bun install
bun run dev:acorn-api     # acorn-backend on 127.0.0.1:8083 (needs MONGO_URI in acorn-backend/.env)
bun run dev:web           # acorn-frontend on localhost:6005
bun run dev:acorn         # watch-build the extension into acorn/extension/dist
```

Load `acorn/extension/dist` unpacked in `chrome://extensions`, set an OpenRouter key and an extension password on the profile in the site, then sign in from the side panel.

- **Where to look when a run misbehaves:** the tab's **Logs** panel, **Problems** view first, then the run's `decision` entries (why it clicked, waited, or stopped) and the `API` entries (what each model call was sent and answered, how long it took); the downloaded zip's `00-summary.json` gives each run's outcome and reason. - `VITE_ACORN_DEBUG=true` (development builds) pins the build's API URL.
- **Tests:** the extension has no unit tests; `bun run test` in `acorn/extension` only checks Prettier, ESLint (no warnings allowed) and `tsc`. `bun test` at the root runs the `*.test.ts` of `@acorn/shared`; `go test ./acorn-backend/... ./acorn-agent/...` runs the backends' (the writer, the selector, the gateway's account isolation, the agent's loop…).
- **End to end:** `bun run e2e:agent` builds the extension and drives it headless against the agent server on a local site (§19.9).
- **Version bumps:** any shipped extension change bumps `acorn/extension/package.json` (docs and tests do not).

## 19. The agent Run (acorn-agent)

The Run is a loop a person would recognise: look at the page, decide what to do with the mouse and keyboard, do it, look again. It is what the sidebar's **Run** button starts. (Until v1.83.0 a page-reading Run, which parsed the page as a tree and decided with rules and counters in the extension, could be chosen instead with an **Agent Run** switch in Settings; both the switch and that Run were removed.)

Written from the code at extension **v1.83**.

### 19.1 The split

| Side                                                      | Does                                                                                                                             | Knows nothing about                          |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **Extension** ([`src/agent/`](../../extension/src/agent)) | Looks (a screenshot, and what the page says about the focused control), acts (real mouse and keyboard events), draws the overlay | What a form is, what to answer, when to stop |
| **acorn-agent** ([`acorn-agent/`](../../../acorn-agent))  | Holds the run's memory, asks the model what to do next, judges whether the last actions worked, ends the run                     | The browser: it never touches a page         |

A change to how the agent decides (the prompt, what it remembers, when it gives up) is a change to acorn-agent only. The extension changes only when the browser needs something new: a new kind of input, a new thing to report about the page.

```text
extension (service worker)                      acorn-agent (hosted, or this computer)    OpenRouter
```

### 19.4 One step

0. **Is the image the size it says?** The server decodes each screenshot and refuses one whose pixels differ from its viewport by more than one pixel (`bad_observation`, "the screenshot is 2560x1314 pixels but the viewport says 1280x657"): the model measures in the image it is shown, so a mismatch would send every click to the wrong place.
1. **Look.** `Observation`: the screenshot (data URL), the page's address and title, the viewport (screenshot size, scroll position, page size, all in screenshot pixels), the focus report, notes (a dialog that was accepted, a tab the run moved into), and the results of the last step's actions.
2. **Is the page moving?** The server reduces each screenshot to a 32 × 32 brightness grid and compares it with the previous one: the page counts as unchanged when no cell moved by 12 or more (a blinking caret and JPEG noise stay under it; typed text, a message or a new page do not). The model is told "the screen looks the same as after your previous actions" and for how many steps. After `ACORN_AGENT_MAX_STALE` (6) such steps in a row the run ends as `stuck` without another model call. A retried step does not count as an unchanged screen.
3. **Find the form (checks on).** On job **posting** pages only: while the run has not yet seen an application form or a clear Apply / Submit / Continue control, the decision model is asked one yes/no question on the screenshot. At `ACORN_AGENT_CHECK_MATCH_PERCENT` (90) or more the driving model is called (if the page was auto-scrolled, the model is told to fill from the top before Submit); otherwise the server sends one scroll down (45% of the viewport height) without calling the driving model, up to 4 times, then asks the driving model anyway. When Jev decides the page text is **not** a job description but is a long application or account page, auto-scroll is skipped. It runs only before the driving model's first look of the run (the model finds its own way after that, so a stop and Continue do not run it again), and never while the extension has attached a note to the look (an emailed code is for the model to type, not for a scroll). The scroll is made at the middle of the screen: the extension refuses a scroll with no point. A survey look, an unfinished plan, or checks being off skip this. Trace entries use `source: "nav"`.
4. **Ask.** The request is the system prompt ([`prompts/system.md`](../../../acorn-agent/agent/prompts/system.md), deliberately short: the task, "analyze the screen and do the next thing that gets the application submitted, doing the best you can with what the screenshot and the applicant's details show", the answer format, the actions, the applicant's profile and the résumés), the run's history, and the current look with its screenshot. The model answers in a strict JSON schema: `observation` (what it sees and whether its last actions worked; written before it decides), `memo` (its own notes, at most 2000 characters: the one thing carried from step to step besides the recent screenshots; `null` means unchanged, so it is not written out again), `job`, `status`, `message`, and `actions[]`, each with an optional `check` (19.4a). An action is one of several shapes ([`schema.go`](../../../acorn-agent/agent/schema.go)), each with only the fields its kind uses: a click is `{kind, x, y, check}`, a type `{kind, text, secret, check}`, a scroll `{kind, x, y, dx, dy, check}`, a wait `{kind, ms}`. Strict mode needs every field of a shape present, so before this every action was 12 fields with about 9 of them `null` (about 50 tokens a click, now about 15). The model writes about 100 tokens a second, so a six-action answer (about 400 tokens) took 3.7 s to read and a long plan would take far longer. `screen` and the `survey` action exist only for a run that may look at a page as a survey, and `check` only when a decision model checks the screen. A field the shape leaves out reads as absent, the same as `null` did. The first JSON object of the reply is read and what surrounds it (a code fence, a stray character after the brace) is ignored; an answer that is still not that JSON is sent back once with the reason (3 of 47 recorded steps needed that before the parser was made lenient).
5. **Check.** Actions are checked before they leave the server: a point outside the screenshot, text to type that is empty or over 2000 characters, a key that is not one, a scroll of no distance, or more actions than the run allows (30 with checks, 6 without) are refused and listed in `dropped` (which the log shows). A `working` step with nothing usable waits 1 s and looks again.
6. **Act.** The extension performs the actions in order, then looks again. `done`, `need_person` and `stuck` end the run; their actions are dropped.

### 19.4b A click that opens a file picker

A file button clicked with a plain `click` opens the browser's file picker; the extension intercepts it, so nothing is attached and the screenshot shows nothing. Three layers handle it. **The prompt** says to use `upload`, never `click`, for anything that takes a file, and not to use a "type or paste the text" option (the agent has files, not their text). **The result** says it: the executor reports `opened: "file_picker"` and the next look reads "this click opened a file picker that you cannot see, and no file was chosen: to attach a file, use upload at this point". **The server** then acts: it draws the clicked point on the current screenshot and asks the decision model what the marked control takes (`résumé`, `cover letter`, `other`); at 0.90 or more for a résumé (`ACORN_AGENT_CHECK_MATCH_PERCENT`) it sends the résumé upload at that point itself, without a model call, and tells the model afterwards. A cover-letter or other-document control, an unsure answer, a failed check or checks being off leave it to the model, which is told what the control looks like it takes. The agent uploads at a point once. The attempt is a trace entry with `source: "picker"`.

### 19.4c The job description, and which résumé

**Only text the page shows is read.** A recorded run did not upload the résumé because the page text it was given held "We've received your résumé. Click here to update it." (a message kept `display:none` until an upload), while the screenshot showed only "Attach résumé or Paste résumé": the model believed the text and wrote "résumé received" in its notes. The page-text reader ([`collectPageText`](../../extension/src/agent/page-info.ts)) now skips every element whose computed `display` is `none` or `visibility` is `hidden`, with its subtree; text off-screen or only visually hidden is still read. The debugger's DOM view (which has no styles) is used only for text inside closed shadow roots and frames a script cannot enter, never for the rest of the page. The prompt and the job-description note also say the screenshot, not the text, decides what is filled in.

A screenshot may never show the job description: clicking Apply scrolls straight to the form. So the extension reads the page's visible text on every look and sends it as `pageText` **only when it changed**. It reads **every frame of the tab**: `collectPageText` runs in each frame through `chrome.scripting` (`allFrames`, so a frame of another origin or another process is read by the browser running the script inside it), walking open shadow roots and same-origin frames; frame texts are labelled by host, merged with the top frame first, and a same-origin frame already inside its parent's text is not repeated. Two signs send it deeper: a custom element with no open shadow root (a closed one) and a tab with more frames than a script could enter; then the debugger's DOM view (`DOM.getFlattenedDocument` with `pierce`) adds the text the scripts missed. At most 24 000 characters. Checked in a real browser with the description in a cross-origin frame on another host, a same-origin frame, an open shadow root and a closed one. The server asks **Jev** (text, about $0.00002 a call) one question about it: does this text describe a specific job, not a sign-in page, a bare form, a company page or a list of jobs? At 0.80 or more the first such page becomes the run's job description (at most 12 000 characters), and the model is told it once, on its next look. At most 6 pages are judged per run, each address once; a page of under 400 characters is not asked about. Checked live: a job posting 0.98, a bare application form 0.03, a sign-in page 0.02.

**The résumé is the server's choice, never the model's.** A résumé stack the model names in an upload is ignored (a live run showed Luna naming the fallback folder itself and bypassing the job description); what it may name is a loose document (a cover letter) or a format (`docx`, or a stack's name followed by a format), which is kept. The stack is the one already chosen for the run, the only one, or the one Jev picks, and the model is told its pick was ignored. The résumé is chosen by Jev from **the whole description** (not the model's one-line `job`, which is now also allowed 1 500 characters). If the run reaches a résumé upload with **no** description, it does not guess: it **asks the person, every time**. The Now card shows "Which résumé should Acorn send?" with **Yes, upload [default]** and **I'll choose**. The default is the résumé the person marked **Make default** in their Acorn Library (`isPrimary`), or, in development with local files, the folder in `DEFAULT_FALLBACK_RESUME` (it must exist, or the run does not start). Yes: the agent sends that résumé at the held point with no model call and tells the model afterwards. I'll choose: the run ends as "Choose your résumé" (reason `resume_choice`) for the person to upload on the page and press Continue. Actions the model planned before the upload run first; those after it do not. A control that takes another document (a cover letter) is never held, a run with a single résumé or no default set is never asked, and nothing is asked once a description was found. The question is a step with `status: "ask"` and an `ask` object; the answer comes back as `answer` in the next observation (`MSG.ANSWER_RUN` from the sidebar to the service worker; Stop ends the wait). A retry before the answer asks again.

**Files only ever come from this computer.** The prompt forbids Dropbox, Google Drive, OneDrive, Box and any other online source, and signing in to one. Only the `upload` action attaches a file. This is a prompt rule (the agent has no list of services to match); a page that opens such a chooser anyway is not blocked by code.

### 19.4f Where the run starts

A run that starts in the middle of a long form fills what is on screen and never learns that required questions lie above it; a plan to send an application is only as complete as the part of the page the model has seen. Two things keep that from happening, both by looking at the screen, not by reading the page:

1. **Every new page is looked at from its top.** The extension scrolls to pixel 0 (instantly, [`scroll-top.ts`](../../extension/src/agent/scroll-top.ts)) before the first look of a run and before the first look of every new address or title, never mid-form.
2. **The model is told what it has not seen, in pixels.** The agent keeps the parts of the page that have been on screen as ranges in screenshot pixels from the top ([`coverage.go`](../../../acorn-agent/agent/coverage.go)), starts them again when the address changes or the page's height changes by more than 12 px (something above moved), and puts one line in each look: "The page is 5560 px tall. You have looked at: 0 to 1591. You have not looked at: 1591 to 5560." Pixels, because the page grows as it is filled in and a percentage shifts under the run. Where the run had to scroll down past a job description to find the form (§19.4a, the form-ready gate), the part above the form is not counted as unseen.
   No look through the unseen parts happens before the application is sent. One was tried (a pass with the decision model over every unseen part, about 26 s on a 5000 px form, which found nothing): it is gone, because pressing Submit makes the page show its own errors on screen, and those are what the model reads next. Starting at the top and the pixel line are what keep a field from being missed.

### 19.4g Dropdowns: the model says what, the decision model finds where

A recorded Reddit/Greenhouse run spent 21 of its 30 model calls (about 4.5 minutes, 70% of its cost) on six dropdowns and a consent box: one click per call, because an option's position is unknown until the list is open, and several wrong picks (the list had moved under the planned point) each cost a correction call. So a page-drawn dropdown is a **`choose`** action: the control's point and the answer in the applicant's words (`text`, at most 200 characters). The driving model plans every dropdown on the screen in one answer, and [`choose.go`](../../../acorn-agent/agent/choose.go) carries each out with the decision model:

1. Send a click on the control (the model is told to aim at the box's value line, not its label).
2. Look: the decision model is asked two things about the screenshot, whether a dropdown list is open (`list_open`) and which option answers (`option`, counting from the list's first option). **If no list is open, nothing is typed**: the click is moved 12 px down, then 24 px down, then 12 px up (`nudgeOffsets`, the point can land on a label or between label and box) and looked at again; typed words with no list open went nowhere, and typed spaces scrolled the page. After the third nudge the model looks.
3. A sure answer (`ACORN_AGENT_OPTION_MATCH_PERCENT`, 70) is picked with `Home`, `ArrowDown` to its position and `Enter` (`Home`, because the highlighted option follows the mouse pointer and is not necessarily the first). With no sure answer the answer is **typed to narrow the list**, because a model counts a few options reliably and many not: live, positions 1 to 5 of an 8-option list were right and "Male" (6th) came back as 6 or 7, which would pick "Non-binary". If the typed words match nothing, they are backspaced out and the whole list is looked at once; if nothing answers then, the rest of the run is dropped and the model looks with the list open and a note saying which answer found no sure match.

The extension only receives a click, text and keys. The agent's own actions have ids `s<seq>ch<n>` and their results are not shown to the model. Each look is a trace entry with `source: "choose"`. With checks off a choose is a click, the typed answer and `Enter`. The answer should be as short as the option would read; the decision model matches it to the option by meaning. The model's `check` on the last action is the one check after all dropdowns; a failed check goes to the repair look of 19.4a.

### 19.4h Scroll management: points stay valid while the page moves

A recorded run (Greenhouse-style application, a native education dropdown) spent 23 model calls going back and forth on one question. The page's scroll position at each look went 598, 854, 989, 769, 842, 952, 989: it moved by itself between looks, so the points the model had measured on a screenshot landed elsewhere (the empty College and LinkedIn fields stayed empty, a date picker opened, and clicks that hit the résumé page's Dropbox and Google Drive buttons were refused by the file-source guard). What moved it: keys sent while nothing had focus (a run of `ArrowDown` scrolls the page about 40 px each, `Home` scrolls to the top with a smooth scroll still running when the next screenshot is taken), a native list's popup (never in a screenshot) taken for "no list open" and clicked again and again, and a field scrolling to keep its caret visible. The fix is five layers, none of them about a site:

1. **Points are pinned** ([`pin.go`](../../../acorn-agent/agent/pin.go)). Every point action of a plan (click, hover, upload, choose) up to the plan's first scroll carries the scroll position of the screenshot it was measured on (`scrollTo`, no page height: a page's height changes as a form is filled). Before acting, the extension ([`scrollForAction`](../../extension/src/agent/survey.ts)) reads the page's position and, only when it has moved more than 3 px, scrolls it back at once; a page that will not go back fails the action so the model looks. Most actions find the page where it was and cost nothing. Actions after the plan's own scroll are not pinned: they were aimed blind. The prompt lets a plan of up to 30 actions (`ACORN_AGENT_MAX_ACTIONS`) scroll on to fields below the screen only where it can aim at them: after a scroll of `dy` pixels what the model saw at `y` is at `y − dy`, and it ends the plan where it would have to guess. The scroll carries a check, and the actions after it run only if the checker confirms it (19.4a).
2. **The page is at rest when it is looked at** ([`scroll-rest.ts`](../../extension/src/agent/scroll-rest.ts)): before each screenshot the scroll position is read every 50 ms until two reads agree (at most 800 ms), so a smooth scroll is not caught half way.
3. **Keys and typing need a control with focus** ([`focus-guard.ts`](../../extension/src/agent/focus-guard.ts)). With nothing focused, a key that scrolls a page (`ArrowUp`, `ArrowDown`, `PageUp`, `PageDown`, `Home`, `End`, space) or typed text would move the page, so the action fails with "nothing has focus … click the control first" and the model looks. A page that cannot be asked is not refused.
4. **A plan ends at its first upload** ([`cutAfterUpload`](../../../acorn-agent/agent/pin.go)). Attaching a file changes the page (a row for it appears and what is below moves), so the points planned after the upload were measured on a page that no longer exists: a recorded run clicked the wrong field, typed into nothing (the layer-3 guard refused it, and the rest of the plan was skipped) and filled nothing. The actions after the upload are dropped and the model is told to plan them on its next look.
5. **A native list is chosen from its options as text** ([`choose.go`](../../../acorn-agent/agent/choose.go)). After the click on a `choose`, a focused `<select>` reports its options (19.4b's focus report); the decision model picks the option by its wording (no counting rows in a picture, which it does badly), and the option's whole text is typed and committed with Enter. An option whose text is exactly the answer (ignoring case and spacing) is taken without asking the model: asked for "No" among "No answer", "No" and "Yes", it split its weight 0.44 and 0.40 and the choose never completed. No arrow keys, Home, or second click, and "is a list open" is never asked of a popup the screenshot cannot show.

### 19.4j Lists that load as one types

A postal-code or address field shows its matches only after the page has asked a server, a moment after the last key, and the answer comes back later; a screenshot taken at once shows no list, so the model or the checker decides on nothing and the dropdown fails. Three things: (1) after any step that typed or pressed a key, the extension waits for the page ([`input-settle.ts`](../../extension/src/agent/input-settle.ts)): 300 ms for the page's own debounce, then until no XHR or fetch request is in flight for 250 ms, at most 2.5 s, before the step is looked at (once per step, not per key); (2) a `choose` whose narrowed list shows nothing is waited for once more (800 ms) before its typing is taken back out; (3) the prompt tells the model to click the option it sees on the screenshot for a list that loads as one types, not to press Enter or arrows before it has loaded, and to choose between typing and clicking by what the screenshot shows. The note a gave-up `choose` leaves says to click the option on the screen.

### 19.4i Several tabs at once

Each tab's Run is its own session on the agent server and its own debugger session in the browser; nothing is shared but the person's model key. Running many tabs is slower for these reasons, none of which is the agent's code: a tab that is not shown **draws no frames**, so (1) its screenshots can wait up to `SHOT_TIMEOUT_MS` (8 s) before the retry that brings it to the front, (2) the page's own timers are throttled, and (3) before this change each point of a plan waited up to 900 ms for the cursor to glide in a tab where it never moves. With Auto-Focus on the tabs take turns at the front every few seconds, so with N tabs a tab is shown about one turn in N, and everything in a background tab that needs a frame waits for its turn. Also, all runs share one OpenRouter key's rate limits, so many runs can see retries (`httpAttempts` in the trace). Changed: in a hidden tab the overlay places the cursor and does not wait for it (the pages's `document.visibilityState`). Each step's log now has `captureMs`, `actionsMs` (the step before's actions) and `hidden`, so a slow concurrent run shows whether the time went to capturing, acting, or the model.

### 19.4m Fast fill (in progress)

The aim is a whole application in about a minute, or less on a short form: one plan for the whole page from one look (a survey), carried out zone by zone, with the check of each zone done on the side while the next one runs, and the dropdowns probed one after another with their option lists read together. Accuracy comes first: nothing here may skip what a page needs to be right.

**The switch.** `ACORN_AGENT_FAST_FILL=on` in `acorn-agent/.env` (the server turns it on for every run, and the extension follows the `fastFill` and `survey` of the start answer), `VITE_ACORN_AGENT_FAST_FILL=true` in `acorn/.env` (the extension's build default, `AGENT_FAST_FILL` in [`agent/settings.ts`](../../extension/src/agent/settings.ts)), or `fastFill` in `AgentRunArgs` is sent in the start request as `fastFill`; the agent keeps it in `Start.FastFill`, says so in the first line of the run's story, and records it in the trace's `session.json`. With it off a run goes step by step, as before; a test holds that.

**Phase 1: the résumé first, then a whole page from one look.** With the switch on:

- **Surveys are on.** The extension surveys (`surveyOn` is true for a fast-fill run) and the agent sets `Start.Survey`, so the model is shown the page as screenshots top to bottom and the reply schema has `screen` and the `survey` action (19.4e).
- **The prompt** has a section "Filling a whole page at once" ([`system.md`](../../../acorn-agent/agent/prompts/system.md)): if the page can fill itself from a résumé, plan only that upload and nothing else; then plan every field of the page in one answer, top to bottom, up to `ACORN_AGENT_FAST_FILL_ACTIONS` (60) actions; do not scroll (the `screen` of each point does it); leave `check` null. The paragraphs that ask for a check on every field and for scrolling inside a plan are left out of this run's prompt.
- **A plan runs as one piece.** `chunkLimit` is `FastFillActions`, not `ChunkActions` (6), so a plan with no checks is not cut every six actions and the rest dropped; it is cut only where the model put a check, at a scroll, or after an upload. Without a decision model the unchecked limit is also `FastFillActions`.
- **The next look is a survey** (`surveyNext` in [`checkpoint.go`](../../../acorn-agent/agent/checkpoint.go)) after an upload (the page moved, and a résumé read may have filled fields), and after the last piece of a plan that clicked, typed, pressed keys or chose, so the model sees the whole page again to finish what is left and to check it. A piece with more of the plan still to run is not followed by one.
  **Phase 2: zones and anchors.** A fast-fill plan is carried out zone by zone:

- **Zones.** A zone is the survey screen an action's point was measured on (`Action.Zone`, set from the model's `screen`; typing, keys and waits take the zone of the action before them, `inheritZones` in [`zones.go`](../../../acorn-agent/agent/zones.go)). A run that is not fast-fill, or a look of one screen, has no zones.
- **A photo at the end of each zone.** [`runActions`](../../extension/src/agent/executor.ts) calls `zoneDone` when the next action is in another zone, and after the last one; the run ([`runner.ts`](../../extension/src/agent/runner.ts)) takes a screenshot with the overlay hidden and sends all of them as `zoneShots` with the next look. A batch whose action failed takes none (the model looks at the page anyway). The agent drops a photo that is not an image of the viewport's size and keeps at most 12, writes them to the trace as `NNN.zoneK.jpg` beside the entry that answers the look (the extension keeps its own copies in the run's log), and holds them for the checks of phase 4.
- **Anchors.** For every point action of the plan (click, hover, upload, choose) the agent keeps a crop of the survey screen the point was measured on: 360 px wide, 100 px above the point and 24 below (`buildAnchors`), its place in the screenshot, the zone and the scroll position. It reaches above the point because a field's label sits there and does not change when the field is filled. A single screenshot is its own one screen. Nothing uses them yet: phase 3 finds a target again with its crop when the page's height changes.

**Stabilising the survey (between phases 2 and 3).** A run of the phase 2 build showed three faults, each with its own fix:

- **The model put points on the wrong screen.** It said screen 7 for the first name, last name and email fields (y 198, 267, 338), which were on screen 6, and the applicant's name was typed into the sponsorship question. Two fixes. (1) Each survey screenshot the model is shown has its number written on a black plate in its top left corner, "SCREEN 6 OF 8" ([`badge.go`](../../../acorn-agent/agent/badge.go)); the copy sent to the model is drawn on, the survey and the anchors' crops are not. (2) In a survey every click, choose and upload also carries a `label`, the control's name as the page writes it, and before a fast-fill plan is carried out each labelled point is checked ([`pointcheck.go`](../../../acorn-agent/agent/pointcheck.go)): the survey screen is drawn with the points numbered on it and the decision model is asked, for each, whether it is on the control that belongs to the label (`ACORN_AGENT_POINT_MATCH_PERCENT`, 70). The screens are checked side by side, so it costs about one check. A point below the threshold is not acted on, nor is what follows it up to the next point (the text typed into it); the rest of the plan runs, the model is told which labels were not carried out and the next look is a survey. A check that fails leaves the plan as planned. A refused point that is on no control but in the field of one (the words of a question, the gap round its box) is first moved onto the control, at the same x, and checked again, the same way ([`reaim.go`](../../../acorn-agent/agent/reaim.go)); only one that is refused again is dropped. The click the model named with `commit` (the one that sends the page or goes on to the next) is held back when the plan lost anything: a refused point, an action that was invalid, an upload that could not be chosen. The model is told which click was not pressed and why, and the next look is a survey: a recorded run pressed Submit twice with a required field unfilled, and read the red text it turned every question into.
- **Every look was a full survey.** The survey is now taken again only where it changed ([`survey.ts`](../../extension/src/agent/survey.ts), `SurveyKeeper`). A screen is reused, not scrolled for, when a photo of its zone was taken when the zone was done, or the last survey has it and the batch just carried out did not touch it; only while the page is as tall as the last survey saw it (±12 px), and only after a batch in which every action ran, belonged to a zone and none was an upload (an upload fills fields all over the page). When every screen is reused the page does not move at all. The log's `agent-survey` entry says how many were reused.
- **The page flashed and seemed to shrink.** Three changes. (1) A survey, the scroll to a pinned action and the scroll to the top of a new page now turn the mouse wheel in small steps (120 px every 40 ms at the page's left edge) and wait for the page to come to rest ([`page-scroll.ts`](../../extension/src/agent/page-scroll.ts)); a page that is still not at the place after three tries is put there at once, so the place is always right. After a scroll that moved the page the survey waits 350 ms for what loads there. (2) The screenshot is taken whole, at the screen's own resolution, with no `clip`, and made smaller in the extension with a canvas ([`capture.ts`](../../extension/src/agent/capture.ts)): a clip with a scale makes the browser resize the page for the moment of the shot, which is the likely cause of the page seen flashing smaller. This is a hypothesis to check by eye; if the canvas is not available the clip is used from then on. (3) Nothing else changed in how the overlay is hidden for a shot. The survey costs more time (about 0.6 s a screen) and is expected to.

**Settled parts and the minimap (1.90.0).** A page is looked at more than once and most of it does not change. In a survey the model also answers `settled`: the screens it will not need to come back to (nothing on them is left to fill, answer, press or check). The agent ([`settled.go`](../../../acorn-agent/agent/settled.go)) keeps them as stretches of the page, in screenshot pixels, merged; a screen the plan acts on in the same answer is not settled by it, nor is one whose point was refused by the check above. They stay settled while the page is the same page. When the form moves (a message appears under a field, a question opens, a résumé shortens it) the stretches follow the page's controls and are not deleted: _The page's controls_ below says how, and that what appeared is not settled. No control moved and the page grew: the new pixels are at the bottom and the coordinates still hold, so a code block appended under the form does not make the finished slices be surveyed again (1.92.2). The page shrank and nothing moved: the bottom is cut off. The fence is still where the plan first acts, and it is no longer what deletes the map. The minimap draws the controls' tops as ticks. Another page forgets everything. The step's answer carries them (`settled`, with the page's `pageHeight` and the `fence`) when they change. They have three effects:

- **They are not taken again.** The extension's survey ([`survey.ts`](../../extension/src/agent/survey.ts)) leaves out a screen that lies wholly in a settled stretch, so nothing scrolls to it or photographs it, and the model is not sent it; the note of the look says which stretches are left out. A survey whose other screens are all left out but one is still a survey. The log's `agent-survey` entry counts `screens`, `reused` and `settled`.
- **They are painted on a map of the page in the sidebar.** The Jobs tab's **Page map** card ([`RunMapCard.tsx`](../../extension/src/sidebar/RunMapCard.tsx), [`page-minimap.ts`](../../extension/src/sidebar/page-minimap.ts)) draws the page as a column, scaled across and down on their own scales, and on it: the settled stretches in the accent with a bar at the left edge; the screens of the last survey as bars at the right edge (photographed, or reused); where the form moved as a hatched band; where the plan first acts as a dashed line; the page's controls as blocks by kind (text box, dropdown, button, check, file; links are left out); the points of the plan as rings and dots (to do, being acted on, done, failed, skipped, and a ring round one that moved with its control or was found again by its picture); and the window as an outlined box that follows the scroll. A caption gives the numbers and a legend the meanings; a badge says what the run is doing (starting, looking at the page, asking the model, acting, waiting for you, ended). The colors are design-system tokens (the chart palette), resolved through the canvas's own style so they follow the theme. The run sends it as `RunProgress.map` ([`page-map.ts`](../../extension/src/agent/page-map.ts), all in CSS pixels) from the moment the tab is open, after each look, as a survey scrolls, as each action begins, is aimed, ends or is skipped (the executor's `progress` hook), and when the run ends; the card keeps the last map after the run. (1.90.0 drew a narrow minimap in the Now card, only while a run on a long page went on; 1.94.0 moved it under the card and made it the page map.)
- **They count as looked at.** The reach of the model's looks ([`coverage.go`](../../../acorn-agent/agent/coverage.go)) now includes every screen of a survey and every settled stretch. Before, only the one screen the extension was on counted, so a model that had been shown the whole page was told it had "not looked at" most of it, and the stop gate's "go through the whole page" sent it scrolling again.

**The page's controls (1.93.0).** The page keeps a list of its controls and where each sits ([`control-marks-page.ts`](../../extension/src/agent/control-marks-page.ts) is the script, [`control-marks.ts`](../../extension/src/agent/control-marks.ts) the pure part, [`control-watch.ts`](../../extension/src/agent/control-watch.ts) the run's side, [`control-sync.ts`](../../extension/src/agent/control-sync.ts) what the run loop wires in). Two things are placed by it: the settled stretches and the points of a plan. Nothing in it asks a model.

- **The list.** Every drawn input, text area, select, button, link, and anything given the role of a button, check, radio or combobox, up to 400, that is not fixed or sticky (a fixed control has a different place on the page at every scroll position, so it says nothing of the form). A mark is an `id`, its `kind`, its place (x, y, width, height on the page, CSS pixels) and its `box`, the field round it: the largest ancestor that holds no other control and is at most 240 px tall, so a point on a question's own words is on its control's field. The `id` is the control's tag, type, name or id, and its label (`aria-label`, the `<label>`, `aria-labelledby`, placeholder, or a button's text); controls that look alike share it with their order and count (`#2/3`), so an id means the same control only while the count is the same. A MutationObserver and a ResizeObserver collect the list a moment after the page changes; the run reads it every 250 ms (only its version when nothing changed), and afresh before each look and each time it asks about a control. A page without the script (a new document) is given it on the first call.
- **What the agent is told.** Each look carries `marks` (the list in screenshot pixels), `layout`, where the form moved since the list the agent was last told of (it is told that list once its answer has come back), and `look`, a name for the look that a step sent again after a failure keeps, so the agent places the move once. Every answer, whoever made it (the model, a check, a probe of dropdowns), carries the settled parts when a look moved them, so the extension's copy says the same as the agent's. The moves are found by pairing the controls that are in both lists, down the old page: each time the distance a control moved changes, the form moved there. A move is `{from, at, dy}` in the old page's pixels: the controls from `at` down moved `dy`, and what lay between `from` (the bottom of the last control above that did not move) and `at` is where something appeared or went. Several moves are several insertions or removals. With no control above to say where the move began, `from` is the top of the page.
- **The settled stretches follow.** [`placeSpans`](../../extension/src/agent/control-marks.ts) (the extension) and `placeSettled` ([`settled.go`](../../../acorn-agent/agent/settled.go), the agent) apply the same rule, and tests hold them to the same answers. The old page is cut into runs that moved as one; each piece of a stretch goes where its run went. What lies in the gap of a move is no stretch's: what appeared there has not been seen, so it is not settled and the next survey takes it. A place that two pieces both land on (the form shrank over it) is not settled either.
- **A point is bound to its control.** When the agent makes a plan it looks up, for each point, the control it is on: the smallest control box that holds it, else the smallest field box, and none when two are as small or none holds it ([`marks.go`](../../../acorn-agent/agent/marks.go)). The action goes out with `mark` (the control's id and place as they were), and the clicks the agent makes for a dropdown carry their dropdown's (`carryAnchor`).
- **A point follows its control.** [`scrollForAction`](../../extension/src/agent/survey.ts) asks the page where that control is now. It must be the same id and the same size (within 3 px in height, 24 in width). If it moved, the window goes where it went and the point keeps its place in the window; then the page is asked whether that point is on the control (`document.elementFromPoint` lands on it, or on its field: the smallest ancestor that holds the point, with no other control in it and not taller than 240 px). If it is, the action goes there. If the control did not move though the page's height changed, the same question stands in for the picture. If the control is gone, another shape, or the point would lie outside the window or on something else (an overlay, a header), the picture is used as before (phase 3). Nothing here lets a point go to a place the page does not agree with.
- **Waiting for the page to be quiet.** In a fast-fill run an action's pause ends once the page has been quiet for 90 ms (at least 60 ms; a click at least 150 ms, since the browser announces a file chooser a moment after the click), no longer than the fixed pause it replaces (350 ms; 175 after typing). Quiet is no change to the page and no animation of it running (the overlay's own and endless ones do not count). A hidden tab, or a page that cannot be asked, is waited on for the whole time, as before; a scroll the model asked for keeps its 500 ms. A survey, and the scroll to a pinned action, wait 350 ms for what loads only when the page moved.
- **The log.** `agent-layout` (the moves, once per change), and `agent-mark` when a bound control moved, could not be found, or the page did not agree its point was on it.

**Phase 3: a target is found again when the page changes shape.** An action pinned to a survey screen carries the page's height then; when the page is not that tall the extension did refuse it (the page's growth moves every point below it) and the model looked again. Now ([`scrollForAction`](../../extension/src/agent/survey.ts)): it scrolls where the action expects its target, takes a screenshot with the overlay hidden and asks the agent `POST /sessions/{id}/locate` where the target is ([`locate.go`](../../../acorn-agent/agent/locate.go)). The agent finds the target's anchor (19.4m, phase 2) on that screenshot: both are reduced to half size in grey, the crop is correlated (normalised cross-correlation, so a brighter screen or a field that was filled does not matter) down the whole screenshot and 24 px either way, and the best place is the target if it correlates at 0.90 or more and no other place away from it is within 0.04. A crop that is too plain to be found by, a target that is gone and two places that look alike are not found, and are not guessed at. If the target is not where the survey saw it, the window is scrolled by the page's growth and tried once more. Found, the action goes to the point that was found; not found, it fails as before ("the page changed shape … and the target could not be found again") and the model looks. An anchor is two 640 px wide crops (wide enough to hold the label at a field's left edge), each enough on its own: one reaches 100 px above the point and stops 10 px above it, the other lies from 20 to 130 px below it. A plan fills a form from the top down, so what is above a target is what the plan itself just filled (and a browser may fill the rest), while what is below it is not yet filled: in the recorded run the single crop above the point held the field above, filled a moment before, and scored 0.76 and 0.85 (1.92.0). When both find the target they must agree within 6 px, when only one does it must match at 0.95 or more, and the places two crops point to are not guessed between. The match takes about 0.3 s; the log's `agent-locate` entries say what was found and how well. From 1.93.0 the picture is the second way: a point bound to a control follows the control first (_The page's controls_), because the crops round a target hold the fields the plan has just filled. In the recorded run `22394a6e` the crops scored 0.66 and 0.61, then 0.81 and 0.69, two batches were abandoned with the rest of their plans, and the model was called again each time.

**Phase 4: each zone is reviewed on the side.** The photo of a zone is sent when the zone is done (`POST /sessions/{id}/shots`, kind `zone`, fire-and-forget; the look after the plan carries it as well, and a zone is reviewed once). The agent ([`review.go`](../../../acorn-agent/agent/review.go)) reviews it while the next zone is carried out: the decision model is asked, in one call per zone, for each field the plan clicked on (the point has a label) and typed into, whether the field labelled so shows what was typed. A secret and a dropdown are not asked about. The reviews are collected at the next look (waiting up to 6 s for one still running); what is wrong ("`"Last Name" does not show "Lovelace" (screen 2)`") is told to the model once, and the look is a survey. `ACORN_AGENT_REVIEW_MATCH_PERCENT` (80) is how sure the model must be that a field shows its value; 0 turns the review off. A batch that ends with an opened dropdown takes no zone photo at its end.

**Phase 5: dropdowns are probed together.** A fast-fill run no longer sets its dropdowns one at a time ([`probe.go`](../../../acorn-agent/agent/probe.go); the script of 19.4 stays for what the probe cannot read). For a run of dropdowns the first batch opens each, waits 500 ms, takes a picture (a `snap` action, which the extension sends with the page's focus to `POST /sessions/{id}/shots` and waits for) and presses Escape; no look comes between. The agent reads the pictures side by side (one decision call each, at once). A good answer among the first 6 options is picked by its place; a native list is picked from its options as text; a list too long to count, one that is not open yet, or one that has to be searched, is opened again with the answer typed and photographed again, still in the batch (then up to 12 options are counted). The next batch picks in every dropdown that was resolved (open it, the keys of the option's place), bottom one first, and nothing checks a pick afterwards: the survey that follows the plan does. The lists are opened from the top down and picked from the bottom up, in the order of their places on the page, not of their places on their own screens (a point's y is on its survey screen: ordering by it alone made the pass go back and forth between screens), so the pass that picks begins where the one that opened ended, and a pick that adds a message moves nothing still to come. The first batch of a run of dropdowns is not followed by a survey, since the run goes on without the model; the run's last batch is. A dropdown whose picture did not come, or that still cannot be read after that typed picture, goes back to the script, which has its own ways (clicking again a little lower, clearing what was typed, telling the model). Every click the probe or the script makes for a dropdown carries that dropdown's anchor (`carryAnchor`), so a height change does not stop the plan on an action the agent made. `ACORN_AGENT_PROBE_DROPDOWNS=off` sets them one at a time.

**The page is never scrolled into a settled part.** Every scroll the run makes by itself ([`page-scroll.ts`](../../extension/src/agent/page-scroll.ts)) knows the settled stretches: a scroll whose window would lie wholly in one is not made (an action's own target is the exception, since it has to be reached), one that crosses a settled stretch crosses it fast (600 px steps 6 ms apart, where the rest go 120 px every 40 ms), and every scroll is written to the log as `agent-scroll` (from, to, why, whether refused). The agent drops a scroll the model planned that would end in a settled stretch and says why ([`withoutBlueScrolls`](../../../acorn-agent/agent/settled.go)). A title that changes is not a new page either: only another address (without its fragment) is, so the page is not scrolled to its top and what was settled is not forgotten when the title changes. The log's `agent-page` entry says what the address was and became.

**After a batch that stopped half way**, a survey does not retake the screens that lie wholly above the fence (the batch changed nothing there): they are reused from the last survey (`SurveyReuse.fence`), unless a résumé was read, which fills fields anywhere. A batch that ran whole is reused only while the page is as tall as it was, as before. A skipped action (one after a failure) is reported as one `agent-actions:skipped` entry with its count and ids, not one `agent-action:failed` entry each; only the action that failed has that.

**Prompt (1.92.1).** The model is told to aim each point on the survey screen where the control is wholly in view and near the middle, never on one where an edge cuts it off; to select with `Control+a` before typing into a text box that shows text or that the page or browser may have filled; and not to settle a screen with fields a résumé may fill while a résumé is still to be attached. A box with no dropdown arrow is text (click and type), not `choose`. Submit is not pressed while a required field is still empty; red "required" beside a field that already shows the right value is stale, so the field is not rewritten and Submit is pressed again. A click that sends the page or goes on carries `"commit": true` (1.93.0).

**A fragment is the same page.** A look is of a new page, which is looked at from its top and forgets what was settled, when its address changes; the address is taken without its `#fragment`, and a changed title is not a new page ([`pageKey`](../../extension/src/agent/page-map.ts), `withoutFragment` in the agent). An Apply button that jumps to the form below (`…#application`) changes only the fragment: before this it counted as a new page, the page was scrolled to its top and what was settled was forgotten, so the next survey crossed the whole page again. The log's `agent-page` entry says when a look was taken for a new page, and the agent's terminal says why what was settled was forgotten (another page, or the page's height).

**A survey is never cut short, and is crossed once.** The overlap of one screen with the next is fixed at 30 px, not a share of the screen, and the number of screens has no limit that a page reaches (`SURVEY_MAX_SCREENS` and `maxSurveyScreens` are 10 000, a guard against a page that grows without end). A recorded run on a page 6,141–6,244 px tall with 791 px screens took 8 screens, 0 to 5,497 px, and never saw the bottom 650–750 px (where the application is sent), because the 9th and 10th positions were cut off. The screens are visited from where the page is: on to the nearer end first, then across the rest, so the way back to the start is not travelled, and the page is left where the last screen was taken (an action pinned to a screen scrolls there itself). The look's note also tells the model that this look is the survey and not to ask for another in the same answer: one run asked for a survey right after receiving one and paid for both.

- **When the page changes shape** (a question that appeared, an error under a field) an action pinned to a survey screen is no longer refused: its target is found again, phase 3 below.

**The baseline** every later phase is measured against, one Greenhouse application (6,246 px tall, about 8 dropdowns, 10 typed fields) up to the submit step, from the run logs:

| Run                        | Total | Driving calls | Decision calls | Session start | First résumé     |
| -------------------------- | ----- | ------------- | -------------- | ------------- | ---------------- |
| Before the history change  | 333 s | 9 · 190 s     | 12 · 49 s      | 16 s          | 20 s (timed out) |
| After history and schema   | 278 s | 12 · 120 s    | 16 · 76 s      | 14.7 s        | 20 s             |
| With the library preloaded | 224 s | 15 · 122 s    | 37 · 38 s      | 0.2 s         | 0.2 s            |

Where the 224 s went: driving calls 122 s (8.1 s each; three of the 15 only scrolled, two used the page's own "Autofill my application" before the prompt forbade it), browser actions 46 s (most of it the dropdown script of open, type, wait, check, clear and arrow keys, one round trip each), decision calls 38 s, looking 7 s. A driving call's time is the provider's wait (about 6.5 s) and the read of about 130 output tokens (about 3 s); sending a request is no longer a cost (about 0.35 s for 100 KB).

**The phases.** (0) the switch and this baseline (done); (1) the résumé upload first, then a survey of the settled page and one plan for all of it (done); (2) the plan run zone by zone, each action's target kept as a small crop of the survey screenshot (done); (3) when the page's height changes, each target is found again by matching its crop vertically (and a little sideways), and a target that cannot be found stops the plan so the model looks (done); (4) each zone's closing screenshot is checked on the side, field by field, while the next zone runs, and what is wrong is fixed once at the end (done); (5) the dropdowns probed together (done); (6) measured against this baseline before the switch is turned on by default.

### 19.4e Survey: the whole page in one look, and fewer model calls

**Off by default.** A survey scrolls the page in front of the person (the screen seems to blink, and a long page takes as many screenshots as it needs and their delay) and was never shown to save calls, time, or money: every recorded run that finished used the current screen only (17 to 37 model calls, about $0.01 to $0.03), and the two recorded surveys ended in seconds. `AGENT_SURVEY` in [`agent/settings.ts`](../../extension/src/agent/settings.ts) is `false`: the extension sends `survey: false` in the start request and every look is the current screen. The agent then leaves "Seeing the whole page" out of the model's prompt (a `{{if .Survey}}` section of `system.md`) and ignores a `survey` action the model gives anyway. The rest of this section describes what happens when it is turned on (`AGENT_SURVEY`, or `survey` in `AgentRunArgs`).

A recorded Greenhouse run took 22 model calls, and 17 of them were mechanical: clicking dropdown options (11) and scrolling to find fields (6). Each call costs about 7 s and $0.0006, mostly output (278 tokens, of which only about 59 were actions; the rest was narration), so the way to a faster, cheaper run is fewer calls, not smaller ones. Three changes, none of which names a site:

1. **Terse answers.** `job` may be `null` (it is written once, when learned, then kept; it was repeated on every call, about 90 tokens), `memo` is a line or two and `null` unless it changed, `observation` is one short sentence, and `message` a few words.
2. **Type-ahead for dropdowns.** A dropdown the page draws itself (a searchable list) is answered by clicking it, typing the start of the answer and pressing Enter, which needs no options on screen, so every dropdown question visible can be planned in one run with a check after each (19.4a).
3. **A survey.** On the first look of a page, and whenever the address or title changes or the server asks (the model's action of kind `survey`, which is never sent to the extension: it sets `Step.survey`), the extension scrolls through the page by itself ([`survey.ts`](../../extension/src/agent/survey.ts)), taking a screenshot every screen less 30 px of overlap, to the very bottom of the page however tall it is (a page under 1.25 screens tall is not surveyed; since 1.90.0 a survey is never cut short, and it is taken with the mouse wheel, 19.4m), then puts the page back. The server shows the model all of them, top to bottom, with where each is scrolled to; the model plans the form in one answer and gives each point action a `screen`. The server turns that into `scrollTo` (the screen's scroll position) and `pageHeight` (the page's height then) on the action, and the executor scrolls there before acting (`scrollForAction`).
   - **It refuses rather than guess.** If the page is not the height the survey saw (± 12 px) or will not scroll to where asked, the action fails with "the page changed shape since the survey… look again", the rest of the batch is skipped and the model looks afresh. A message that appears above a field, or a row added by an attached file, moves every point below it, and a click at a stale point lands on the wrong control. Each run of at most `ACORN_AGENT_CHUNK_ACTIONS` (6) actions is also checked by the decision model (19.4a).
   - **Not a text observer.** The survey is screenshots only; the extension has no DOM serializer (§7).
   - **Cost:** a survey is as many screenshots as the page needs, once per page, and screens the model settled or the run already has are not taken again (19.4m) (about 1.3k tokens each) which stay in the cached history; the checked run then replaces the call-per-scroll and call-per-dropdown pattern.
4. **A run that ends for the person scrolls first.** With `need_person` or `stuck` the model may send up to two scroll actions, which the extension runs before it ends the run, so that what the person must act on (a code field, a CAPTCHA) is in view when they look.

A trace entry with a survey writes `NNN.survey1.jpg`… and, for a screen that has actions on it, `NNN.survey1.marked.jpg` with them drawn.

### 19.4k Accounts: guest first, own e-mail and password, never single sign-on

The prompt's "Accounts" section sets the order. The agent signs in or signs up only when the application cannot be sent without an account; a guest route, "continue without an account" or a skippable sign-in is taken first. When an account is needed it uses the applicant's profile e-mail and `defaultAccountPassword` (typed through the `{{account_password}}` placeholder, so the password is in no prompt or trace). Then: sign in; if the site rejects it, sign up with the same details (an activation link stops with `verification_link`); if the sign-in still fails, use "forgot password" and stop with `verification_link` for the reset link, then set the account password as the new one and sign in; otherwise stop with `account_rejected`. The e-mailed link is read from the connected Gmail like a code (19.6b).

Two things back this up in code:

- **Single sign-on is refused.** The vet check (19.4d) asks Jev a second question in the same call: whether a control, window or frame signs in through another service's account instead of the employer's own e-mail and password form. A probability of `ACORN_AGENT_SSO_BLOCK_PERCENT` (50) or more blocks the click, or closes the window or frame, with `cause: single_sign_on` in the verdict; the model's next look says to use the employer's own form or continue as a guest. Live, single sign-on buttons, windows and frames scored 0.80–0.98 and the employer's own "Sign in", "Create account", "Continue as a guest", "Forgot your password?", "Next" and "Submit application" 0.02–0.20. No service is named in code.
- **A rejected account ends the run.** Steps that type the account password are counted ([`agent.go`](../../../acorn-agent/agent/agent.go): `entersSecret`, `accountRejected`). Past `ACORN_AGENT_ACCOUNT_ATTEMPTS` (8) the run ends stuck with `account_rejected` instead of going round the forms to the step limit, and the notice asks the person to sign in themselves.

### 19.4l Résumé autofill first

The prompt's "Résumé autofill" section tells the model to use a page's way of filling itself from a résumé before typing any field: an upload that reads the résumé, or a button or link that fills the form from a résumé file ("Autofill with résumé"). Only a résumé file may fill the form: a second paragraph forbids any autofill that draws on a profile or saved application kept at the job board or another service, on another service's account, or on a control that first asks to connect or sign in ("Autofill my application", "Use my saved application"). When both are offered the résumé one is taken; when only the other is, the model ignores it and types the fields from the applicant's details. It uploads with `upload` (never a click) or presses the control, waits for the page to finish reading, then checks every field against the screenshot and fixes or fills what is wrong or left, since a read can be partial. Typing first is wasted: the page overwrites it. Only a file from this computer counts: an import from another service or from an online profile link is refused by the guard (19.4d, 19.4k). The plan still ends at the first upload (`cutAfterUpload`), so the next look sees the page as the résumé changed it. It is prompt-only: no code path decides that an autofill exists or what it draws on, the model reads that from the page. The guard of 19.4d judges only online file sources and sign-in through another service, so an autofill of the other kind is held back by the prompt alone.

### 19.4d Files only from this computer: the guard

The applicant has not allowed any online file source (a cloud drive, a file-sharing service, signing in to one), so no click may reach one. The prompt says so, but a model can slip, so three things are enforced in code, with no list of services in it (the decision model says what a control or page is, and was right on all 20 realistic cases tried live: Dropbox, Google Drive, an icon-only OneDrive button, a Google Picker frame and an OAuth window all scored 0.91–0.97; Attach, Choose file, Next, Submit, a recaptcha frame, Calendly and an ATS apply window scored 0.02–0.09; "Enter manually" 0.46).

1. **Before a click** (`click`, `double_click`, `triple_click`, `right_click` and `upload`): the executor reads the control under the point from the page (`guard.ts`: through shadow roots and same-origin frames; its text, `aria-label`, `title`, image descriptions, link host, id and classes, and whether it sits in a group around a file input) and the server's `POST /sessions/{id}/vet` asks Jev one question about it. It starts while the cursor glides, so it adds no wait; a plain form field is skipped, and the same description is judged once per run. A probability of `ACORN_AGENT_VET_BLOCK_PERCENT` (30) or more blocks the click: it is never sent, the batch stops, and the model's next look says "blocked: that control uses an online file source… attach a file with upload".
2. **After a click**: a window the click opened is judged (address, title and the start of its text) before the run moves into it, and is closed if it is an online file source or a sign-in to one. A frame of another origin that appears in the page is judged the same way (by address) and removed. Frames are found by sweeping the page after each click and before each screenshot (frame events only trigger a sweep); the sweep is the one that sees a frame of another process. Only a frame a person could see is judged (at least 40 × 40 px, not hidden): a live run closed a one-pixel Google API proxy frame the page loaded for itself, and told the model a click had opened it. The note now says only that a frame showed an online source.
3. **Fail closed where it matters.** A control the decision model cannot be asked about is blocked when it sits in a file-upload component and let through otherwise; a window or frame that cannot be judged is let be (a failed check must not close every page an application opens). Every decision is a line of `vets.jsonl` in the trace, and costs about $0.00002.

It is a model's judgment, so it cannot be proven complete: an icon-only control with no text, name, image description or class, in no file component, is the case it can miss before the click, and then the window and frame checks are what catch what it opens. The browser tests cover a Dropbox button (refused, never clicked), a window opened by a neutral button (closed) and a frame opened the same way (removed).

### 19.4a Plans and checks

With a decision model configured (the default), the model plans a whole screen at once and puts a `check` on an action: a short description, in its own words, of what the screen should show once that action has run ("First name field shows Stanley"). When the plan fills **two or more** `type` fields before any `scroll` or `upload`, each with its own check, the server sends **one run** for that prefix only and the checker confirms every expectation in a single look; any `scroll` or `upload` in the same answer is queued for later runs after that check; if that fails, the model gets the screenshot and a note to look at every field on the screen and put every wrong or empty one right together in one answer (it used to fill the rest one action and one check at a time, which cost one call per field). An **`upload` always ends a run** (Greenhouse and similar pages autofill and move fields after a résumé), and a **`scroll` never shares a run with actions before it**, so the checker confirms the screen before the page scrolls and the next clicks stay on the right controls. Automatic navigation scrolls toward the form only when no plan and no pending check are waiting. Otherwise the prompt asks for a check at least every `ACORN_AGENT_CHUNK_ACTIONS` (6) actions and the server cuts the plan into **runs** that end at a check (or at that limit) and sends the first run only. After the extension reports its results and a new screenshot:

1. If a result failed, or the screen did not change, the plan is dropped and the model looks (nothing to check). A run that typed text or pressed a key is the exception: a few characters in a field move too few pixels to register, so the checker is asked instead (a live run dropped the rest of its plan after typing a phone number).
2. Otherwise the decision model (`openai/gpt-6-luna-decisions` by default, `ACORN_AGENT_SCREEN_MODEL`) is shown the screenshot and asked three yes/no questions: does it show what the model expected (`matches`), is the page blocked by a popup, overlay, CAPTCHA, sign-in wall or page-level error, not a small validation message beside a field (`blocked`), is it still loading (`loading`).
3. `matches ≥ 0.90`, `blocked ≤ 0.20` and `loading ≤ 0.30` (`ACORN_AGENT_CHECK_MATCH_PERCENT`, `_BLOCKED_PERCENT`, `_LOADING_PERCENT`): the next run is sent **without calling the model** (the person keeps seeing the model's last line). `loading ≥ 0.70`: the agent waits 1 s and checks again, up to 4 times in a row. Anything else, or a checker that fails: the plan is dropped, the model looks, and its next look says how many of its planned actions ran and why the rest did not. A checker that fails once is not used again that run, and plans are then cut to 6 actions.
4. A run whose end has no check ends the plan there: the model looks next and is told the rest did not run. When the plan is used up the last run is still checked if it had a check, then the model looks and is told it ran in N parts.

The model is the only thing that plans or recovers; the checker only says yes or no. The expectation text, the thresholds and the questions are generic: nothing in them names a site, a vendor or a page's wording. `ACORN_AGENT_CHECKS=false` turns all of this off (plans are then cut to 6 actions and the prompt does not mention checks). A check is recorded in the trace as an entry with `source: "check"` (19.8); its cost is in `Usage.checks` / `checkCost`.

**Actions** (every one is something a person does): `click`, `double_click`, `triple_click`, `right_click`, `hover` (at a point), `type` (into the focused control; `secret` marks a password or code so it is never logged), `key`, `scroll` (at a point, by a distance), `upload` (a résumé, at the control that opens the picker or takes the drop), `wait`. The model also has `choose`, which is never sent to the extension (19.4g).

### 19.5 Memory and context

- **History** is append-only and carries one screenshot: the current step's. Every earlier step is replayed as the text it was sent with and the model's answer; its screenshot is not sent again (the text says "Screenshot no longer kept."), and the agent frees it from memory. Sending old screenshots made each request bigger (181 KB at step 1, 842 KB at step 9 in a Greenhouse run) and the upload alone took up to 24 s. `ACORN_AGENT_KEEP_IMAGES` (default 0) sets how many earlier steps' screenshots are sent again; above 0 it slides a window and changes the prompt from the oldest kept turn on at every step. Nothing earlier changes between one step and the next, so the provider's cache still holds: it bills tokens that repeat the start of an earlier prompt at **$0.01 per million instead of $0.125** (19.11), and a screenshot is never part of the replayed start, only of the current message. The history is compacted only when its estimated size passes `HistoryTokens` (30 000; screenshots no longer count, so this takes many steps): all but the newest `ACORN_AGENT_KEEP_TURNS` (8) steps are folded into one line each ("step 4: Filled the address [type …; key Tab]", at most 80 lines of 240 characters). Then it grows by appending again. There is no second model call for this.
- **Memo.** The model's own scratchpad (19.4) is how the run remembers what is done and what was tried, without relying on what is still on screen. It is told to the model on every step ("Your notes so far") and stays in each replayed step as it was; repeating it costs a hundredth of the normal price once cached, so it is not stripped from older steps (that would change the prompt).
- **Résumé.** (The choice is made from the job description and may ask the person first: 19.4c.) When the model emits an `upload` it usually names no file; the server picks a _stack_ (a folder): a name the model gave if it matches a file, a stack (optionally with a format: "C# + React docx") or a loose document, else the stack chosen earlier in the run, else the only stack, else **Jev** (`typesafe/jev-1.13`) chooses among the stacks by name given the job the model recorded (loose documents are never offered). The stack is sent as a PDF unless a format is named (formats are tried pdf, docx, doc, rtf, txt). If Jev fails the first stack is used and the step's `dropped` says so.
- **Secrets.** The model reads the profile without Acorn's own keys and logins. The account password appears as `{{account_password}}`; when the model types that, the server types the real password and marks the action secret, so the password is in no prompt, history or trace. The OpenRouter key kept in `profile.json` is used only when the server has none of its own.

### 19.6 Stopping, failing, and the person

- **Done.** The model reports `done` once the page shows the application was received. When a Run is started with `stopBeforeSubmit` (tests only) it reports `done` at the control that sends it, without clicking, and the run ends as "Ready to submit".
- **Needs the person** only for what the applicant's own hand must give: a CAPTCHA (`captcha`), a code sent to them (`verification`) or a link in an email they must open (`verification_link`), an identity number the profile lacks such as an SSN, driver's license or passport number (`identity`), a document that is not among their files such as a diploma, transcript, ID scan or work permit (`document`), or a sign-in the application cannot go on without when the profile has no account password (`sign_in`). A site that rejects the account after the steps in 19.4k ends the run as stuck with `account_rejected`. The model answers every other question itself: when the profile does not say (worked here before, used this tool, served in the military, may we text you, how did you hear about us) it chooses what most applicants choose and notes it in its memo. With `need_person` or `stuck` it returns `stop: {reason, problem, action}` in plain words; the server adds `no_change` (the page stopped moving) and `step_limit`. The Now card shows it as a notice (19.2). An emailed code or link is read from the applicant's Gmail by the extension (19.6b).
- **Stuck.** The model's own report, the unchanged-page limit, or the step limit (`ACORN_AGENT_MAX_STEPS`, 150). Continue after the step limit adds another budget of that many steps.
- **Errors.** `no_key`, `invalid_key`, `no_credits`, `rate_limited` and `model_error` map to the same plain-words messages as the rest of Acorn (`@acorn/shared/user-messages`); a server that is not running says so.
- **A new tab.** When a click opens a tab, the run moves into it (the old one stays open), tells the model, and Stop follows. A page-opened tab is found by `webNavigation.onCreatedNavigationTarget` (a tab the person opens with Cmd+T or + does not count), and one closed before the run gets there is skipped: the run stays in its tab.

### 19.6b Emailed codes and links

When the agent ends a run as `need_person` with reason `verification` (a code) or `verification_link` (a link), the extension reads the applicant's connected Gmail instead of stopping ([`mail-verification.ts`](../../extension/src/agent/mail-verification.ts), `POST /acorn/run/mail-verification`, backend [`mailcode`](../../../acorn-backend/mailcode/mailcode.go)). **Whether it is a code or a link is the model's word** (the stop reason), never a guess from the page's wording: a word search once read a page that asked for a code as a link, searched for a link, and found nothing in 14 looks.

- **`since`:** only mail that arrived after the site was asked to send can be the site's (an earlier email's code is no longer valid). It is the time the last actions that change a page began (a click, typing, a key, an upload: `CHANGES_THE_PAGE` in [`executor.ts`](../../extension/src/agent/executor.ts)), not the time of the last wait or scroll, which come after the site has already sent.
- **Which text is the code** is not judged from a shape, and the decision model reads the email. A recorded run offered only tokens that held a digit or had no lowercase letter, so a code of mixed-case letters (`qGEZpnBb`) was never a candidate and "18th" from a sentence was typed; the next version masked each candidate in its words and the real model, asked live, answered "none" for the right one (0.27 to 0.68). What works, tested against the real model on four email shapes (mixed-case letters in their own element, digits in their own element, a code inside a plain-text sentence, a verify link among others; three runs each, with a long unrelated page text in the state): the **email's text is part of the state**, and each candidate is only its own text (`The code is "qGEZpnBb".`) or, for a link, its text, address without the query and the words before it. The candidates are taken from the email by code, never written by the model: first the texts that **stand alone** (each innermost HTML element, or line of a plain email, whose whole text is only a code-sized run of letters and digits: how a site sets a code apart, true of any letters and digits), then tokens inside sentences that look like codes ([`extract.go`](../../../acorn-backend/mailcode/extract.go)). The model chooses among them (certainty 0.95 to 1.0 for codes; about 0.5 to 0.6 for a link, which is chosen but not by a wide margin). The value must still be found written in the email, and when the model answers none its most probable candidate is used only at 0.5 or more. The model therefore reads the code (it already reads each email's preview, which usually holds it); the link's query string, where sites keep the token, is never shown to it.
- **A retry** (the site asked again, because a code was wrong or was resent): the emails already used are sent as `exclude`, so only a newer email can answer, and the search starts from the first search's `since`, not from the typing that followed it (typing the code had moved `since` past the very email that held it).
- **Each look** (every 5 s, 10 minutes at most) lists the 10 newest emails; the decision model weighs those after `since`, and the newest plausible ones are opened to find the code or link, which is confirmed to be written in the email before it is used. The backend answers with the emails (sender, subject, time, whether after `since`, whether weighed, the chance given), the emails it opened (what each held, never a value), the decision model's name and, when found, the email's id.
- **Shown on the Now card** ([`MailSearchPanel.tsx`](../../extension/src/sidebar/MailSearchPanel.tsx), `RunProgress.mail`): what is being read (code or link), since when, how many looks, then each email with its chance, "Before the request" for mail that cannot compete, and "Used" on the one the value came from. It stays after the search, so a miss can be read. The code (or the link's address without its query) is shown once found. Each look is also written to the log (`mail-verification:look`: sender, subject, time, chance, and for each email opened what each candidate was offered as, what the decision model answered (how many it saw, whether it chose, the likeliest and how sure) and which was used; no addresses or ids).
- **Found:** the agent is continued (19.6a), told the value in its next look ("Acorn read this verification code…"), and types it itself (the prompt says so); a link is opened in the tab. **Not found or no Gmail:** the run ends as "needs you" (or "Gmail is not connected").

**The applicant is asked last** ([`stopgate.go`](../../../acorn-agent/agent/stopgate.go)). A recorded run stopped at a CAPTCHA after 7 model calls with the optional fields (website, LinkedIn, date available, desired pay) still empty. So a stop for the applicant (`need_person`, `stuck`) is not accepted at once: the first one of a run is **sent back** (the step is a 300 ms wait with the message "Finishing everything else on the page before asking you.", and the model's next look carries a note telling it to go through the whole page from its top, fill every field it can from the applicant's details, optional ones too wherever those details answer them, take every other action that does not need the applicant, and say in its observation what it checked). Its next stop stands. A stop made while some pixels of the page have not been looked at (19.4f) is sent back again, up to `ACORN_AGENT_STOP_PASSES` (2) times in a run; 0 accepts every stop at once. The prompt says the same, so the model stops last on its own, and the gate catches it when it does not. This costs one model call on a stop, and it does not change what the model may stop for.

**"Done" is the page's confirmation, not the model's word** ([`donegate.go`](../../../acorn-agent/agent/donegate.go)). A recorded run ended `done` with the form still open, the résumé not attached and nothing submitted, because the model decided the posting's location requirement excluded the applicant, and the person was shown "Application sent!". When the model reports `done` (a run that was not asked to stop before sending), the decision model is asked of the screenshot whether it confirms a submitted application (`application_sent`: a thank-you or confirmation, not an open form, an error or a posting). Below `ACORN_AGENT_DONE_CONFIRM_PERCENT` (70) the `done` is sent back (the step is a 300 ms wait and the model's next look says what done means, and that a posting's own requirements are no reason to leave an application unsent), up to `ACORN_AGENT_DONE_PASSES` (2) times; after that the run ends as **stuck** ("The application was not confirmed as sent", reason `page_problem`), never as sent. A checker that cannot answer does not refuse the model's word. The prompt now also says: apply even when the posting's requirements look unmet, and answer experience questions in the applicant's favour (yes, and the most years the career supports). Checked live against the recorded screens: open forms read 0.00 sent; no recorded screen of a confirmation exists yet, so a false "not confirmed" on a real confirmation page is untested.

### 19.6a Continue

Continue takes a stopped run back up **in the same conversation**: the model keeps its notes, the job it recorded, the history, the résumé it chose and the cost so far, and the step numbers go on. It is not a new run.

- **What stops a run and can be continued:** the model's `need_person` or `stuck`, the unchanged-page and step limits, the résumé question answered "I'll choose", the person pressing Stop, and a failed call (the connection, a busy model) that exhausted its retries. A run that finished, a tab that closed, and a session the server no longer holds cannot.
- **Extension.** When such a run ends, the runner does not delete the session: it hands `{sessionId, runId, tabId, stopBeforeSubmit}` to [`kept-run.ts`](../../extension/src/agent/kept-run.ts), under every tab the run used, and the Now card shows **Continue** (`RunProgress.canContinue`). Continue (`START_RUN` with `continueRun: true`) takes the kept run out of storage ([`background/messages/run.ts`](../../extension/src/background/messages/run.ts)) and calls `POST /sessions/{id}/continue` instead of opening a session. It works in the tab the run stopped in, even if Continue was pressed on another tab of the run, and writes to the same log and trace folder (the same `runId`); the run keeps the `stopBeforeSubmit` flag it started with, since the agent's prompt was fixed then. A fresh **Run** on the tab ends the kept session; closing the tab the run worked in ends it too (`chrome.tabs.onRemoved`).
- **If the agent forgot the session** (it restarted, or the session sat untouched for an hour): when a run stops, the runner also fetches `GET /sessions/{id}/memory` (best effort) and keeps `{memo, job, jd, resume, formReady}` beside the session id. If Continue then gets `no_session`, it opens a new session seeded with that memory (`POST /sessions` with `memory`) instead of starting over: the job description is not looked for again, the résumé chosen from it is kept, the model's notes and job come back, the form is not searched for again, and the run keeps its Stop-before-Submit setting. The sidebar says "The agent was restarted. Acorn kept the job description, your résumé choice and its notes, and goes on from them…". The model is told the earlier steps are no longer held, so it judges by the screenshot; the step history and cost counters do restart. Without kept memory (the memory fetch failed before) it starts over as before. A fresh **Run** still clears everything.
- **Server.** `Agent.Continue` clears what belonged to the stopped moment: the unfinished plan and its checks, an upload held for the person's answer, the unchanged-screen count (the person's help is not a stalled screen) and the loading waits. It adds a note for the next look: "You stopped the run (the reason). The applicant has pressed Continue, so they may have changed the page since. Look at the screen as it is now and carry on from your notes; do not redo what they say is done." For a run that was only interrupted (Stop, a dropped connection) the note says the last actions may not have run, so the model judges by the screenshot. After the step limit the budget grows by another `ACORN_AGENT_MAX_STEPS`.
- **Expiry.** A session untouched for an hour is dropped (`SessionTTL`), so Continue after that finds `no_session`; the extension then says "The agent no longer remembers this run, so it starts over…" and starts a new run on the page as it is. The kept session holds the person's Acorn token and the history in the agent's memory for that hour.

### 19.8 Data and privacy

- The screenshot and the shaped `profile.json` (§19.5) go to OpenRouter (the model); the decision model that checks the screen gets the screenshot and the model's own sentence about what it should show (no profile); Jev gets the job text, the shaped profile and the résumé stack names. Nothing goes to acorn-backend, and the extension keeps no copy of the profile.
- **In production the agent is a hosted server** (19.12), so the screenshots, the shaped profile and the person's Acorn session token pass through it on their way to OpenRouter and acorn-backend. It keeps a run in memory only and ends it (and forgets the token) when the run ends, a deploy restarts it, or the session sits unused for an hour; its traces are off, so nothing is written to its disk; its log holds routes, statuses and counts, never bodies, keys or tokens. Anyone who can read that server's memory while a run is live could read that person's profile, so the host is as trusted as the API.
- A page's password boxes are not hidden from a screenshot: the model sees the dots, and the focus report replaces a password's value with its length. The password the agent types comes from `profile.json`.
- **Traces.** With tracing on (the default), each run writes a folder `traces/<session>/` on this machine, in the order the steps were asked (a retried or failed step is its own numbered entry, never overwritten): `session.json` (the page, model, limits and the résumés on offer), `system.txt` (the standing prompt, the profile with secrets as placeholders), and for every entry `NNN.jpg` (the screenshot the model saw), `NNN.marked.jpg` (the same screenshot with each action's point drawn, numbered in order: red ring and cross for a click, a blue line for a scroll, green for an upload), `NNN.json` (what the page reported, the unchanged-screen count, what the model decided, the actions sent back, those refused and why, the error if the step failed) and `NNN.model.json` (every model call of the step: the messages sent with their images counted, the raw answer, finish reason, tokens, cost, time, requests made). `timeline.txt` is one line per entry to read a run at a glance. Text typed into a field marked `secret` is written as a character count. The folder holds the applicant's pages and is git-ignored. A trace is the recorded run to replay against a change to the agent. The server's own log has one line per step (status, actions, refused, time, cost, message, error).
- The tab's local log (the Logs tab) holds the `agent-*` events: step, status, message, actions as kind and place, failed actions, retries, cost. It holds no typed text. It also holds the run's **trace** (below).
- **The Agent Run's trace.** The extension starts every run with `trace: true`. The agent then builds, for each entry, the files its trace folder holds (`NNN.json`: what the page reported and the model decided; `NNN.model.json`: every model call's messages, raw answer, tokens, cost, and latency; `NNN.marked.jpg` and `NNN.surveyK.marked.jpg`: the screen with each action drawn on it; the run's `session.json` and `system.txt`) and returns them in the answer (`Step.trace`, `Started.trace`: `AgentTrace` in the shared contract) instead of writing them: the hosted agent still keeps nothing on disk. The extension writes them to the tab's log as `agent-file` entries (title = file name, text = content, an image as base64), with the screenshots it took itself (`NNN.jpg`, `NNN.surveyK.jpg`, numbered by `trace.seq`) and one `timeline.txt` line per entry. `agent-step` events also carry `captureMs`, the time the extension spent capturing (survey scrolling included), beside `ms`, the round trip. Agent files are not shown in the Logs tab. **Download** (`sidebar/log-zip.ts`, `agent-files.ts`) puts every run in `agent/<run>/` of the zip with its `summary.txt` (model calls and time, tokens and cost, checks) and `timeline.txt`. A support report carries the agent files' text but not their pictures, to stay small. The entries count towards the log's 50 MB and five-run limits.

### 19.9 Tests

- `go test ./acorn-agent/...`: the loop against a scripted model and a scripted decision model (history, folding, repair, lenient parsing, notes told once, plans continued, handed back, waited on, cut at an unchecked run, a failing checker, usage and cost of checks, refusals, unchanged-page detection, résumé choice, secrets in traces, 20 runs at once), the model and decision clients against stand-in servers, the HTTP routes, the applicant files.
- `go run -C acorn-agent ./cmd/tracesum [trace folders]` summarizes recorded runs: model calls and repairs, tokens (and how many the provider served from its cache), checks and their outcomes, cost, seconds, and the time spent outside the model.
- `bun run e2e:agent` ([`tests/e2e/agent/run.ts`](../../../tests/e2e/agent/run.ts)): a real browser with the built extension, the real Go server, a form with a native list, a checkbox and a file input, and stand-ins for the model and the decision model. It checks the form received every value, the overlay shows and is removed, the server was sent a screenshot and the applicant, the screenshot's pixels are the viewport the model is told **at two device pixels to a CSS pixel**, Stop works, a planned run is checked and continued by the decision model with two model calls for the whole form, a screen that is not as expected goes back to the model, and a missing server is reported plainly. It brings its own server on a free port and its own build of the extension, so it never touches a server you are running or the extension you have loaded. Real model runs are recorded under `acorn-agent/traces/` and measured in 19.11.

### 19.10 Known gaps

1. **GPT-6 Luna** has completed real applications on real pages (19.11), accepts images, the strict schema (including `check` and a nullable `memo`) and plans actions with checks. Whether `reasoning` other than `none` keeps the JSON in the message is unverified. How often a real plan's runs match what the model expected, and so how many model calls checks save over a whole application, is measured only on recorded pages, not on a complete live run.
2. **Native lists and typeahead.** Clicking a native `<select>` and typing the start of an option selects it in the e2e; ArrowDown then Enter does not. The prompt says to type. Platform differences are untested.
3. **Frames.** The focus report sees the focused control through shadow roots and same-origin frames; a cross-origin frame (an embedded application form) reports no focus. Clicks and typing work there, since they are coordinates.
4. **Mail verification** needs a connected Gmail (19.6b); without one, or when no email matches within 10 minutes, the run ends as "needs you".
5. **Background tabs** may not draw frames; a screenshot that does not come is retried with the tab brought to the front, which is visible. Many tabs at once is untested.
6. **Résumé choice** reads the stack's folder name, not the résumé's text.
7. **`stopBeforeSubmit`** (tests only) relies on the model not clicking the control; nothing outside the model enforces it.
8. **The tab's log holds no screenshots**; they are in the server's trace folder.
9. **Checker accuracy** is checked on a handful of real screenshots: it said "blocked" for an ordinary inline validation message until the question was narrowed (19.4a). A false "matches" lets a bad plan run to the end of its run (at most `ACORN_AGENT_CHUNK_ACTIONS` actions); a false "blocked" only costs a model call. The thresholds are untuned.

### 19.12 Where the applicant comes from, and how the agent is deployed

**The applicant.** The agent holds no database. `acorn-agent/applicant` has a `Source` with two implementations, chosen when the server starts:

- **`files`** (development; `ACORN_AGENT_BACKEND_URL` unset): `data/profile.json` and the folder `data/resumes/` on this computer, as before. A default résumé named by `DEFAULT_FALLBACK_RESUME` that is not a folder there stops the run from starting.
- **`backend`** (production; `ACORN_AGENT_BACKEND_URL=http://acorn-api:8083`): the signed-in person's own profile and Library in acorn-backend. The extension sends the person's Acorn session as `Authorization: Bearer …` when it opens a run; the agent keeps it in memory for that run only and uses it for two calls: `GET /acorn/agent/applicant` when the run starts (the profile and the files, named and typed, without their text: `acornapi/agent.go`) and `GET /acorn/agent/resumes/:id` when the page's file field is about to get a file. A person who is signed out gets `signed_out` (401, "You're signed out" on the Now card), a profile never saved gets `no_profile` ("save your profile on the Acorn website first"), and a backend that cannot be reached `backend_unreachable`. A run only serves the files it was told about, so one session cannot ask for another file's id.

In backend mode a Library stack is a title (the same title in several formats is one résumé), a cover letter is a document by its title, `isPrimary` is the person's default, and generated résumés are not offered. The default résumé offered when no job description was found is the person's own primary one, the résumé they marked **Make default** in the Library (the server has no setting for it; `DEFAULT_FALLBACK_RESUME` is ignored in this mode). If their default is a cover letter, or none is marked, nothing is asked. The OpenRouter key is the person's own from their profile (the server has none of its own in production), and the profile reaches the model as before: hidden fields dropped, the account password as a placeholder.

**Where it runs.** In production the extension's default agent address is the API host, `https://api.acornapply.com`, where nginx sends `/agent/v1/` to the agent container and everything else to the API (`ACORN_PRODUCTION_AGENT_ORIGIN`; a development build uses `http://127.0.0.1:8093`, `VITE_ACORN_AGENT_URL` overrides either). Screenshots, the profile text and the session token cross the network to that server, so the hosted agent turns **traces off** (`ACORN_AGENT_TRACE=false`: no screenshots or profile on its disk) and holds each run in memory only; a deploy ends the runs in flight.

**Deployment** (`.github/workflows/docker-publish.yml`, `docker/deploy-remote.sh`): `acorn-agent/Dockerfile` builds the agent without the Go workspace into `omnimuh730/acorn-agent`, tagged with the commit like the others. `docker/changed-images.sh` rebuilds it when `acorn-agent/*` or the shared `acorn-backend` packages (`config`, `jev`, `llmhttp`, `openai`, `requestid`) change (and everything when the deploy scripts do). The container joins the `acorn` Docker network, reaches the API as `http://acorn-api:8083`, publishes `127.0.0.1:8093` (`ACORN_AGENT_PORT`) for nginx (the `/agent/v1/` block of `deploy/nginx/api.acornapply.com.conf`: 40 MB bodies for a survey, 6 minute reads for a step), and gets only the `ACORN_AGENT_*` and `OPENROUTER_API_KEY` lines of `/opt/acorn/deploy.env`, never the database or Google settings. Deploy refuses to start if that host port is already published by a non-Acorn container. CI builds, vets and tests the module in its own job; after a deploy a public health check of the agent warns (does not fail the API's deploy) when the host is not set up. A rollback to a commit from before the agent leaves the running agent alone.

The extension logs `agent-resume` (`base64Chars`, `encodeMs`) for each file it fetched.

Reading it: a long `waitMs` is the provider (compare `provider` and the cache columns of `usage`); a long `connectMs` with `connReused: false` is a cold connection; `networkMs` large against `serverMs` is the path between the extension and the agent; `lookLaps.shot` large with `hidden: true` is a background tab (§19.4i); `laps.uploadProcessing` or `batchLaps.inputSettle` large is the page's own network.

### 19.11 Cost and time

**Prices** are OpenRouter's catalogue on 2026-10-15 (`GET /api/v1/models`), per million tokens: **GPT-6 Luna** $0.10 input, $0.50 output, $0.01 cache read, $0.125 cache write; **GPT-6 Luna Decisions** $0.10 input and **$0 output**, image input, no cache fee; Jev 1.13 $0.042; cheaper decision models that read images exist (Perplexity pplx-decider and Inception mercury-decide, $0.02).

**What a call really costs.** Fitting the `cost` OpenRouter reports for 11 Luna calls to the token counts, the bill is exactly: tokens served from the prompt cache at $0.01, **every other input token at the write price, $0.125**, output at $0.50. So a token is 12.5 times cheaper when it repeats the start of the previous prompt, and uncached input costs 25% more than the catalogue's input price. The history is therefore append-only (19.5).

**Measured, before this change** (three recorded real runs): 19, 21 and 28 steps (20, 23 and 31 model calls, 6% of them repairs of an invalid answer); 10.0–11.1k input and 230–300 output tokens per call; **$0.0205, $0.0226 and $0.0347** per application (about a third of the input was served from the cache); 4.9–5.4 s per call; wall time **2 m 23 s, 2 m 25 s and 3 m 43 s**, of which 20–25% is the extension acting (about 0.4 s per action and 0.7 s per step). A screenshot is about 1.3k input tokens. The model's notes were only about 60 of its ~250 output tokens per step.

**Measured, append-only history** (8 consecutive real Luna calls on recorded screenshots, no checks): the cached share of the input was 73%, 77%, 82%, 86%, 85%, 87% and 89% from the second call on (each call's cache covered the whole previous prompt); **$0.0004–0.0005 per call against about $0.0011**, 4.2–5.9 s per call (no faster; the wait is the output and a fixed delay). One decision-model check with a screenshot: 1.1–1.6k tokens, **$0.00011–0.00016**, about **0.8 s** from this machine (1.5 s on a cold connection), not 0.1 s.

**Estimates for a 28-step application** (a model fitted to the numbers above, not a measurement of a whole run; re-measure with `cmd/tracesum` after a real run):

| Change                                                                                   | Cost                     | Time (model + extension) |
| ---------------------------------------------------------------------------------------- | ------------------------ | ------------------------ |
| Before                                                                                   | $0.035                   | 3 m 43 s                 |
| Lenient JSON (no repair calls: 31 calls become 28)                                       | −9%                      | −7%                      |

Why checks are about neutral: once the prefix is cached a model call costs about $0.0006, so seven avoided calls save about $0.004, but a call that plans a whole screen writes about 220 more output tokens (+$0.0001 and about +2 s each) and the checks cost $0.0014 and 8 s. They pay only if Luna plans long runs, that is, if calls fall by more than about a third. Run with `ACORN_AGENT_CHECKS=false` and with it on, and compare the two traces.

Where the time goes (3 m 43 s): about 75% is model calls (about 5 s each: a fixed delay of about 2.5 s plus about 7 ms per output token), about 25% the extension acting. Only fewer calls, fewer output tokens or a faster executor move it.
