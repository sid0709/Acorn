# Work log: hosted agent, landing page, legal pages, run traces (October 15 to 16, 2026)

This is a record of what changed, why, and what still needs a person. It is not the architecture reference: [`architecture/extension.md`](architecture/extension.md) describes how the system works and was updated alongside each change. Branches: `feat/enhance-agent` (pull request #43), `feat/enhance-landing` (#45).

## 1. The agent reads each person's profile and résumés from the database

**Before:** `acorn-agent` read `data/profile.json` and `data/resumes/` from the machine it ran on. That works for one person on one computer, not for a hosted service.

**Now:** the agent asks `acorn-backend`, with the signed-in person's own session token.

- **Backend routes** ([`acorn-backend/acornapi/agent.go`](../../acorn-backend/acornapi/agent.go)): `GET /acorn/agent/applicant` returns the profile and the list of uploaded files (no extracted text); `GET /acorn/agent/resumes/{id}` returns one file's bytes. Both need a valid session.
- **Agent** ([`acorn-agent/applicant`](../../acorn-agent/applicant)): an `applicant.Source` with two implementations, files (development) and backend (`ACORN_AGENT_BACKEND_URL` set). The profile is shaped the same way for both: hidden fields dropped, the account password replaced by a placeholder. The token stays in memory for the run.
- **Extension**: sends `Authorization: Bearer <token>` when it starts a run. A signed-out person gets the normal sign-in message.
- **Default résumé:** when a page shows no job description, the agent asks which résumé to send. It offers the one the person marked **Make default** in their Library on the website (`isPrimary`). `DEFAULT_FALLBACK_RESUME` now applies only to local-file development.

## 2. Deployment

- **Image and CI:** `acorn-agent/Dockerfile` (new), an `agent` job in `.github/workflows/ci.yml`, and `docker/changed-images.sh` builds the agent image when `acorn-agent/` or `backend-core/` changes.
- **Publish workflow:** `docker-publish.yml` builds and pushes the agent image and deploys it with the other images. A public health check on the agent only warns on failure.
- **Run script:** `docker/deploy-remote.sh` runs the agent container on the `acorn` Docker network. It reaches the API privately at `http://acorn-api:8083`. It publishes `127.0.0.1:8093` (`ACORN_AGENT_PORT`; port 8090 belongs to another service on the VPS, so the script refuses it). It passes the container only its own settings, not the database or Google secrets. Traces are off on the server.
- **One public domain:** the extension reaches the agent at `https://api.acornapply.com/agent/v1/`. nginx sends `/agent/v1/` to the agent and everything else to the API. There is no `agent.acornapply.com`. The reference block is in [`deploy/nginx/api.acornapply.com.conf`](../../deploy/nginx/api.acornapply.com.conf) (40 MB bodies, 6-minute reads, its own rate limit).
- **Failures seen on the first deploy:** SSH login was refused (the deploy key was not authorized for the deploy user), then `touch /opt/acorn/deploy.env: Permission denied` (the directory was owned by root, not the deploy user). Both are server setup, covered in [`deploy/server-setup.md`](../../deploy/server-setup.md).

## 5. The Logs tab's Download now holds the Agent Run

**Problem:** Download built its zip from the old DOM pipeline's entries. An Agent Run left almost nothing in it, and the hosted agent keeps no trace on disk.

**Now:** the agent returns each step's trace in its answer instead of writing it (`Step.trace`, `Started.trace`), and the extension keeps it in the tab's log. Download puts every run in `agent/<run>/`:

- the screenshot the agent saw (`001.jpg`) and the one with the actions drawn on it (`001.marked.jpg`)
- what the page reported and the model decided (`001.json`)
- every model call: messages, answer, tokens, cost, latency (`001.model.json`)
- `session.json`, `system.txt`, `timeline.txt`, and `summary.txt` (model calls and time, tokens, cost)

The log's `agent-step` event also records `captureMs`, so "capture slow", "network slow" and "model slow" can be told apart. A support report carries the text, not the screenshots. Server and extension code: [`acorn-agent/agent/trace.go`](../../acorn-agent/agent/trace.go), [`src/agent/trace-log.ts`](../extension/src/agent/trace-log.ts), [`src/sidebar/agent-files.ts`](../extension/src/sidebar/agent-files.ts).

## 6. Page survey turned off; the agent sees the current screen only

**What a survey is:** on the first look and after address changes, the extension scrolled the whole page from top to bottom, taking up to 8 screenshots, and sent them to the model at once. This is what made the screen blink at the start.

**Why it is off:** it was meant to save model calls, but no recorded run that finished used one (those took 17 to 37 calls, about $0.01 to $0.03, 1.5 to 3.8 minutes). The two recorded surveys ended in seconds. `AGENT_SURVEY` in `src/agent/settings.ts` is `false`; the extension sends `survey: false`, and the agent leaves surveys out of the model's prompt and ignores a request for one.

**Measured cost today:** about 7 seconds per model call and about 18,500 input tokens per call, mostly cached; model calls were about 84% of a 3-minute local run.

## 6a. Scrolling: start at the top, and tell the model what it has not seen

**Problem found in the logs:** a run began with the form already scrolled down, filled the lower fields, and never saw the empty First Name, Email, Phone and Résumé fields above. With the survey off, nothing made the agent cover the page.

**Now (image-based only):** every new page is looked at from its top, and each look tells the model which pixels of the page it has and has not seen. A "look through the unseen parts before sending" pass was built and then removed: it cost about 26 seconds on a long form and found nothing, because pressing Submit makes the page show its own errors. Details: architecture doc §19.4f. Files: `acorn-agent/agent/coverage.go`, `acorn/extension/src/agent/scroll-top.ts`.

## 6b. A recorded Reddit run: why it took 6 minutes and $0.023, and what changed

The run (30 model calls, 46 screen checks) spent 21 calls and about 4.5 minutes on six dropdowns and a consent box (one click per call, wrong picks corrected one at a time), 26 seconds on the pre-submit look, and then never typed the emailed code.

- **The code was not typed.** After the code was read, Continue reset the form-finder, which judged the screen "not a form" (69%) and sent four scrolls without calling the model; the scrolls had no x/y, so the extension refused them, and the note holding the code was used up by those steps. Now the form-finder runs only before the model's first look, never when the extension attached a note, its scroll has a point, and the prompt tells the model to type the code and send it in one answer.
- **Pre-submit look removed** (see 6a).
- **Dropdowns are a `choose` action** (architecture doc §19.4g): the model gives each dropdown's answer in one plan; the decision model reads the open list and the agent presses the keys. Expected: about 5 or 6 driving-model calls for the form instead of 30.
- **A failed batched check no longer switches to one field per look.** The model gets the screenshot and is asked to fix every wrong or empty field in one answer.
- **`timeline.txt`** in the downloaded zip had lines running together; each entry now ends with a newline.

Not measured: no run has been made with these changes. The target is 40 seconds and $0.005 for a Greenhouse form; the estimate from the recorded run is 55 to 65 seconds and $0.006 to $0.008.

## 6c. A second Reddit run: the code was searched for as a link; Gmail now shown on the Now card

- **Why the code was not typed:** the extension chose between "code" and "link" with a word search over the page's text, and chose "link" for a page that asked for a code; the Gmail search then found nothing in 14 looks. The model now says which, with a new stop reason `verification_link`. The time the search counts mail from was also too late (after a wait step, so a fast email could count as "before the request"); it is now the time of the last click, key, typing or upload.
- **The Now card shows the search** (`MailSearchPanel`): the emails read, the chance the decision model gave each, which one was used, and "Before the request" for mail that cannot compete. Each look is in the log as `mail-verification:look`.
- **Type errors in the Gmail files fixed:** `authHeaders()` is async and was spread as if it were an object (`mail-verification.ts`, `gmail-connection.ts`).
- **Dropdowns (`choose`):** the model's answers were typed into the control first, so an answer worded unlike the option emptied the list, and a click on a label scrolled the page. It now opens the list and reads it first, and types only when the open list has no sure answer.

## 6d. Third and fourth Reddit runs: the code was still not typed, and the dropdowns were slow

- **The code.** The Gmail search found the right email (94 to 96%) but the code was not used. First cause: the extractor never offered a mixed-case letters-only code. A first fix still failed live: with the candidate masked in its words the real model answered "none". It now reads the email's text and chooses among the texts the backend took from the email; a live test against the real model (`mailcode/live_test.go`, skipped without a key) passes on four email shapes. A retry excludes the email already used and keeps the first search's start time; the code is shown on the Now card.
- **The dropdowns.** The model's click often landed on a control's label, so no list opened; the agent then typed into nothing, retried, and the model took over, ten steps for six dropdowns. It now checks that a list is open (nothing typed otherwise), moves a missed click onto the box, narrows the list by typing, and presses Home then ArrowDown to the option. Not tested against a page: the real decision model was run on screenshots from the log (list open or not: right; 1st to 5th option: right; 6th to 8th: unreliable, hence the narrowing).

## 6e. The applicant is asked last

A run stopped at a CAPTCHA after 7 model calls with the optional fields empty. A stop for the applicant is now sent back once so the model goes through the whole page and fills everything it can first (and again while parts of the page are unseen, at most twice); the prompt says the same. Not tested against a real page: the unit tests prove the gate, not that the model then fills the optional fields.

## 6f. The page scrolled by itself between looks

A native dropdown (education level) took 23 model calls: the page's scroll position moved 598, 854, 989, 769, 842, 952, 989 between looks, so planned clicks missed (empty fields, a date picker opened, the file-source guard refused clicks that landed on the résumé page's Dropbox and Google Drive buttons). Causes: scrolling keys sent with nothing focused, a native popup that screenshots cannot show taken for a closed list and clicked again (my `choose` flow did this), and smooth scrolls still running at the next screenshot. Now: points are pinned to their screenshot's scroll and the page is put back before each action; the page is at rest before each look; scrolling keys and typed text are refused when nothing has focus; a native list is chosen from its options as text. Not run on a page: unit tests only, plus the log as the evidence.

## 6g. The résumé was not uploaded: hidden text on the page

Scroll management worked (10 model calls, 98 s, $0.0065). The résumé was never uploaded because the page text the model read held a message the page keeps hidden until an upload ("We've received your resume"); the screenshot showed the empty field. The page-text reader now leaves out elements that are not displayed, and the debugger's unstyled view no longer adds them back.

## 6h. Clicks that missed: the layout shifted after the upload, and "No" matched "No answer"

The résumé uploaded, and the run took 14 calls, 92 s and $0.0100, but two things still cost calls. After the upload the page moved, so the clicks planned after it (in the same plan) landed on other controls; the typing that followed was refused (nothing had focus) and the rest of the plan did not run. And the felony dropdown (options "No answer", "No", "Yes") was never set: the decision model gave "No answer" 0.44 and "No" 0.40. A plan now ends at its first upload, and an option that is exactly the answer is taken without the model. Not run on a page.

## 6i. "Application sent!" for an application that was never sent

A BambooHR run ended `done` after 8 calls with the form open and the résumé not attached: the model decided the posting's location requirement (live in PA, NJ or DE) excluded the applicant and reported done with a message saying it had not submitted, and the extension celebrated. Two runs in that tab, one after the other (16:48 and 17:49), no overlap: running several tabs with Auto-Focus did not cause this; each tab is its own session and the wrong word is in the model's own recorded answer. Fixed: a `done` is checked against the screenshot and sent back, then reported as not confirmed, never as sent; the prompt says not to skip an application over the posting's requirements and to answer experience questions as favourably as the career allows.

## 6j. Many tabs at once are slower

A tab that is not shown draws no frames, so its screenshots can wait up to 8 s and (until now) every point of a plan waited up to 900 ms for a cursor that cannot glide; with Auto-Focus a tab is at the front about one turn in N. The cursor wait is gone in hidden tabs, and each step's log has `captureMs`, `actionsMs` and `hidden` to show where a concurrent run loses time. Not measured: no concurrent run's log has been read yet.

## 6k. Dropdowns whose options load from a server

The screenshot was taken before an autocomplete list (postal code) had arrived, and the run relied on keys. The extension now waits for the page's debounce and its in-flight requests after typing; a `choose` waits one more beat before giving up on a narrowed list; the prompt says to click the option seen on the screenshot for such lists. Not run on a page.
